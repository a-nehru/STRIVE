# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

STRIVE (formerly Star Harbor / "Rehab Suite") — a webcam-based upper-limb rehabilitation game suite for stroke patients, developed by Synapse Lab, Shirley Ryan AbilityLab. UI copy convention: no em dashes in patient-facing text. Plain static site: vanilla JS ES modules, no build step, no dependencies to install, no tests or linter. MediaPipe Pose is loaded from CDN at runtime (internet required on first load). Design decisions are grounded in two rehab papers (CFI framework, Rehabilitation Gaming System) — README.md has a table mapping paper concepts to code; SPEC.md and DESIGN_BRIEF.md hold the full spec and visual design language.

## Run

```
python -m http.server 8321
```

then open `http://localhost:8321` (or double-click `start_game.bat`). A server is required — camera access is blocked on `file://` pages. Testing requires a webcam and allowing camera access; data persists in the browser's localStorage under the key `rehabsuite-v1` (do not rename the key — it would orphan patient data).

**ZED 2 (optional):** `python tools/zed_bridge.py` runs the ZED SDK's depth-based body tracking (BODY_38) and streams it on `localhost:8322` (`/status`, `/stream` SSE skeletons in MediaPipe 33-landmark layout, `/video.mjpg` mirror preview). Each skeleton carries `lm` (normalized 2D) **and `lm3` (the same joints in metres, camera frame: x right, y down, z forward)** — the depth channel `tracker._ingest3`/`hand3(side)`/`has3D` expose and the assessment turns into a real workspace volume; a webcam has no depth, so the volume is simply absent there rather than estimated. With the staff-drawer "Camera source" setting on Auto (the default, stored device-level in localStorage `strive-cam-source`), `tracker.js` probes the bridge at boot and uses the ZED when it's up, webcam + MediaPipe otherwise; the source is chosen once at boot, so changing the setting reloads. In ZED mode **grasp comes from the MediaPipe 21-point hand model run in the bridge** (Sep 2026, by request, the way `zed_track.py` does it): `HandWorker` in `zed_bridge.py` is a thread of its own with one VIDEO-mode landmarker per side, fed every 2nd frame a square crop of the **full-resolution** left image about each of seat 0's wrists (`hand_crops`: nudged towards the fingertips, 150-460 px sized by the shoulder width in pixels; the crop is what makes a hand at 4 m detectable at all), measuring the curl on the model's **world landmarks** (`mp_curl`, no foreshortening), and the freshest result rides in the payload as `hands: [{side, pts, curl}]` with the 21 points levelled for camera roll and normalised like `lm` (`--hands off` disables; `/status` says `hand_model` and `hand_ms`; the model file is the shared gitignored `tools/models/hand_landmarker.task`, downloaded on first use). `tracker._startZed` feeds them to `_ingestHands` (proximity matching, unchanged) with the curl, which `handCurl` returns in preference to the image-point ratio; the curl band now has `zed_track.py`'s hardening too (`CURL_CAL_GROW`, `CURL_CAL_MAX_RANGE`, `CURL_PLAUSIBLE`). Only when the bridge reports no hand model does the browser run the model itself on the MJPEG preview (`_loadHands` in `init`, the loop in `_startZed`), a weak fallback at ward distances; BODY_38's own fingertip heuristic is the last resort. **The preview is read, not `<img>`-loaded (Oct 2026):** `tracker._openPreview` fetches `/video.mjpg` itself, splits the multipart stream on each part's Content-Length (`splitMjpeg`, exported and unit-testable), decodes each complete JPEG with `createImageBitmap` and draws it on a canvas that stands in for the `<video>` (expando `videoWidth/readyState/naturalWidth`); an `<img src=/video.mjpg>` paints progressively, so a frame copied mid-arrival showed its top half new and the rest stale ("the picture loads half way"). **Camera picture (Oct 2026, by request):** the bridge and `zed_track.py` open the ZED at **HD2K, 2208×1242, 15 fps** (`PROFILES`; `--res HD2K|HD1080|HD720|VGA` and `--fps` override, `pick_fps` clamps the rate to what the size supports, `RES_FPS`, since HD2K only does 15): the full sensor makes a hand at 4 m big enough for the hand model, and at 60 fps the sensor could never expose longer than ~16 ms, so a ward without studio light came out dark, flat and noisy. The hand crop band (150-460 px) was tuned on a 1280-wide picture and scales with the width (`REF_WIDTH`), and the hand model and the MJPEG preview take every frame at 15 fps (every 2nd at 30) so neither loses rate; the preview is still downscaled to `--preview-width` (640). Both also push the SDK's picture settings after open (`apply_picture`: brightness 6, contrast 5, gamma 9 of the SDK's 4/4/8 defaults; `--brightness/--contrast/--gamma`, and `--exposure fixed --exposure-val N --gain N` to leave auto exposure) and print what the camera reports back — the ZED's ISP is tuned for stereo matching and, unlike a webcam driver, lifts nothing on its own. **Camera roll is corrected in the bridge (Sep 2026, by request):** a ZED clamped a few degrees off level tilted the trunk the posture coach watches and the y-up frame the assessment measures in, so `Tilt` reads the IMU's accelerometer each frame (`get_sensors_data`, specific force in the image frame, sign-normalised so y is positive), takes the roll about the optical axis as `atan2(gx, gy)`, smooths it slowly, and `body_to_lm` turns every 2D keypoint about the image centre by that angle (`level_px`) while the MJPEG preview gets the same turn with `cv2.warpAffine`, so the skeleton, the people markers and the picture stay in step; `/status` reports `tilt_deg` (applied) and `tilt_raw_deg` (measured). `--tilt auto` (default) | `off` | a fixed angle in degrees; the applied turn has hysteresis and is held still (27 Oct 2026, by request: the picture shook and rotated when the roll read about the old single 0.4° cut-off): it switches on past `ON_DEG` 0.8°, off under `OFF_DEG` 0.4°, and moves only in `STEP_DEG` 0.3° steps (`Tilt.settle`, `Tilt.applied`), and anything past 30° is refused. Only roll is corrected (pitch and yaw do not tilt a person in the picture), and the 3D `lm3` is left alone because positional tracking runs with the SDK's default gravity-aligned world origin. **Distance is lenient on purpose:** patients are in a ward bed or chair 5-15 ft away, so `--max-range` and `--play-far` default to 5 m, `--play-width` to 4 m, and the welcome screen's `framingMessage` only asks them closer below a 0.03-frame shoulder width (about 5 m on the ZED's lens) and accepts a body anywhere in the middle 70% of the picture; seeing them is what matters, SW units make the distance irrelevant downstream. Requires ZED SDK + pyzed on the machine; the game itself never needs it.

**Two players (ZED only):** `python tools/zed_bridge.py --bodies 2` streams two seats. Seats are assigned by **where people stand** (seat 0 = left-most in the image at lock time), then followed by ZED tracking id — never by confidence, which is what would hand a paddle to the other player mid-rally. A seat is held through `--seat-grace` seconds of occlusion, then re-seats to the nearest unclaimed body; `GET /relock` forces a re-seat. Who is a candidate at all is decided **first by where they stand**: `in_play()` admits only bodies inside the play volume (`--play-near`/`--play-far` metres deep, `--play-width` metres wide about the camera axis; defaults 0.6-5 m x 4 m since Sep 2026, for ward beds 5-15 ft away), so a therapist standing behind the patient is never in the running whatever the detector scores. Tracking ids do not survive somebody leaving the room, so each seat also remembers a **build signature** — biacromial width, torso length and height in metres from depth, EMA-smoothed, matched within `--sig-tol` when a free seat is refilled (`build_signature`/`sig_distance`). That is deliberately **not** face recognition: no extra model, no biometric stored, and enough to tell apart the two or three people actually in a therapy room. The payload keeps seat 0 as the top-level `lm`/`lm3`/`shm` (the single-player game reads it unchanged) and adds `bodies: [{seat, id, lm, lm3, shm}]` **and `people: [{id, x, y, sw, z, seat, play}]`** — everyone in view, seated or not, at the shoulder midpoint in normalized image coordinates. **Staff pick the patient by clicking (Sep 2026):** with two or more people in view the welcome screen draws a ring on each (sage = followed, amber dashed = *Click to follow*, `drawPeopleMarkers` in `main.js`) and the staff drawer lists them as buttons (`renderPeople`, with left/middle/right and distance); a click calls `tracker.selectPerson(id)` → `GET /select?id=N[&seat=S]` → `Seats.pin`, which makes the seat **sticky**: it follows that tracking id, bypasses the play volume, relearns the build signature from that person, and once they are gone refills only by signature match or when exactly one person is in view — never by who stands left-most, so a visitor cannot take the patient's seat. `?clear=1` lets a seat float again; `/relock` clears everything. `tracker.js` routes seat 1 into `_ingestSecond` — a deliberately thin second body (shoulders, wrists, trunk only) exposing `armAngle2(side)`/`p2TrackingOk`, touching none of `pts`/`anchor`/`frame`, so compensation, grasp, relocation and the DDA can never be moved by a second person in the room. Pong's `duo` mode uses it: each player's arm side is chosen once in `renderDuoSetup` (`main.js`) and fixed for the round, player 2 is a saved patient whose own `arcMinDeg/arcMaxDeg` drives their paddle (guest = default arc), an untracked player 2's paddle **holds position** rather than snapping to center (a snap would gift a point), the round-1 tutorial is skipped (it is a solo speed measurement), and `score.ai` doubles as player 2's tally. The mode needs the ZED: one webcam pose model reports a single body, so the tile explains itself instead of failing mid-round.

Two ZED tools sit beside the bridge, both reusing its `PROFILES` and `resolve_indexes()`, plus `tools/zed_common.py` (the shared `Readout` that turns one BODY_38 skeleton into the overlay and the numbers — so the two tools can never report different values for the same pose; it imports opencv lazily so the diagnostic can still run and *report* a missing opencv), so they test the path the game actually uses (stop the bridge first — one process at a time can hold the camera): `python tools/zed_test.py` is the staged diagnostic (pyzed import, CUDA GPU via `nvidia-smi`, device enumerated, open, measured fps, depth validity, BODY_38 detection rate, biacromial width, and whether the landmarks the game needs actually fill in), exit 0 when every stage passes, and during the body stage it shows the RGB feed with the skeleton and the live tracking numbers (`--no-preview` for headless); `python tools/zed_view.py` is the live window (skeleton, per-joint XYZ in the SDK camera frame, the same points in SW units with a 1-SW ring, 3D elbow flexion, `armAngle` elevation, and the grasp state replayed with `tracker.js`'s own `GRIP_*` constants so it agrees with the game). Run them from Windows Python, not WSL — WSL cannot see the camera without USB forwarding. The ZED needs no manual calibration (factory-calibrated, SDK self-calibrates at open); the calibration that matters is the in-game assessment, plus letting the fingertip grip envelope widen by opening and squeezing a few times.

**`tools/zed_track.py` (Sep 2026, step one of the rebuild)** is a single-file realtime viewer with no imports from the other tools, run with `py -3.12` (the only Windows Python with pyzed). It shows the ZED's **left RGB eye** (mirrored) and nothing else; every number comes from the SDK's 3D body tracking (BODY_38, model FAST / MEDIUM / ACCURATE, switchable live from an on-screen dropdown or `n`). Per arm: shoulder/elbow/wrist/hand XYZ in metres (camera frame) and the hand from the shoulder in the body's own frame (out / up / forward, cm), **elbow flexion** (0 = straight, computed in 3D), and the shoulder as the ISB pair of **elevation** (0 = arm down, 180 = overhead) in a **plane of elevation** (0 = out to the side, 90 = straight ahead, negative = behind) named with the therapist's word (abduction / scaption / flexion / across / extension). Projected flexion/abduction angles are deliberately not shown: they flip between +180 and -180 once the arm is above horizontal in the other plane, so a real posture (arm abducted overhead) would read as noise. The body frame is rebuilt from shoulders, hips and nose, so the angles do not change when the patient sits at an angle to the camera (checked by yawing a synthetic body). **Grasp** defaults to the **MediaPipe 21-point hand model** (`tools/models/hand_landmarker.task`, downloaded on first use, gitignored) run on a square crop of the RGB frame around each ZED wrist, one VIDEO-mode landmarker per side so the two hands are never confused, about 9 ms per crop on the CPU; the curl is `tracker.js`'s `handCurl` (mean fingertip-to-wrist over palm length, about 2 open and 1 for a fist) measured on MediaPipe's **world landmarks** (metric, hand-centred 3D) so a hand turned edge-on or pointed at the lens does not foreshorten into a fist, then run through the same `CURL_*` band and self-calibration, with one hardening the game does not have yet: the band may only **grow** by `CURL_CAL_GROW` (0.02) per frame, its span is capped at `CURL_CAL_MAX_RANGE` (1.4) and values outside `CURL_PLAUSIBLE` are ignored, because one wild frame lifting `hi` to 3.0 put "open" out of a real hand's reach for minutes and the right hand read CLOSED for ever after (the first live session showed exactly that). The band is drawn under each arm panel (observed range, the close and open thresholds, the hand's current curl) so a calibration problem is visible rather than inferred. The ZED's own four BODY_38 hand points remain selectable (dropdown or `g`) but are too coarse to call open/close reliably. With more than one person in view every body gets a thin grey skeleton and a *click to track* label; the chosen person is followed by the SDK's tracking id (click, Tab, `0` clears, `--person ID`), never by per-frame confidence, and if they drop out the viewer **waits** rather than swapping to whoever is left, adopting a lone person only after 3 s because the SDK hands a returning person a fresh id. `--demo` runs two figures built from known angles with no camera, `--snapshot x.png` renders one frame and exits, `--log arm.csv` appends every frame's positions, angles, grasp state and which models produced them, and keys pick the arm (1/2/3), mirror (m), labels (x) and reset the grasp band (c).

**Tracking lab (Oct 2026, by request: try other models and see which is good):** `tools/handmodels/` is a small package of tracking models behind one interface, `tools/model_lab.py` (port 8326) runs every ticked one on the same frames, and `tools/tracking-lab.html` (open from the site, `http://localhost:8321/tools/tracking-lab.html`; `tools/model-lab.html` is the older browser-side bench) shows the overlays, a strip of what each hand model saw in its crop, and rolling numbers (fps, ms, detection %, landmark jitter, curl and aperture mean ± sd per hand model; detection %, joints, wrist jitter and bone-length CoV per body model, in 3D metres for the ZED). ## Deploy

Live site: **https://a-nehru.github.io/STRIVE/** — GitHub Pages, deployed automatically from `main` of https://github.com/a-nehru/STRIVE (legacy branch build, repo root). To publish: commit, push, wait ~1–2 min. **Always bump the `?v=N` query on the `style.css` and `main.js` references in `index.html` in the same commit** — Pages caches assets for 10 min and browsers hold them longer; the version bump is what makes deploys show up immediately. Verify a deploy by curling the live file for a string unique to the new commit, not just HTTP 200.

## Architecture

Data flow: webcam → MediaPipe Pose (`tracker.js`) → body-relative coordinates → assessment (`assessment.js`) → per-arm profile → games (`games.js` on `engine.js`) → round stats → DDA (`dda.js`) → updated params → localStorage (`storage.js`). `main.js` is the app shell that wires screens, rounds, and the staff/therapist UI together.

### The coordinate system (everything depends on this)

All game/assessment positions are in **shoulder-width units (SW) relative to the shoulder midpoint, y-up** — camera-distance independent and comparable across sessions. `tracker.js` owns the conversions: `handRel(side)` (hand in SW), `relToPx`/`pxToRel` (SW ↔ canvas pixels), `pxPerSW(canvas)`, `armAngle(side)` (arm elevation in degrees vs the trunk axis, 0 = down, 180 = overhead), plus `palm(side)` and `handClosed(side)` (grasp detection — used by Harbor Crates grab/release, Pong skill shots, the assessment squeeze, and the palm disc on the skeleton). Grasp runs two-tier: a dedicated **Hand Landmarker** (21 pts/hand, every 2nd frame, matched to pose wrists by proximity) gives finger-curl via `handCurl(side)`, with **self-calibrating per-person thresholds** (`curlCal` envelope: once enough curl range is seen, "closed" = 35% into that patient's own range, so a partial squeeze still registers; fixed 1.25/1.55 hysteresis until then); if it has no fresh detection, a self-calibrating pose-fingertip heuristic (`grip(side)`) is the fallback. Video coordinates are mirrored (`x = 1 - lm.x`) so the game acts like a mirror. A **stereo webcam** (a ZED plugged in as plain UVC, with no bridge running) delivers one double-wide `left eye | right eye` frame; `tracker.isStereo` (aspect ≥ `STEREO_RATIO` 2.6) detects it and everything reads `srcW`/`srcH` instead of `videoWidth/Height` — `_detectSource()` feeds both models a left-eye crop and `drawVideoMirror` blits only that half, so the patient never sees the room twice and MediaPipe never searches a squashed 2:1 image.

Envelope-based targets and the assessment circle are centered on `CENTER` (exported from `engine.js`) — **the body centre**: the assessment sets it to `{0, 0}`, the shoulder midpoint that is the origin of the SW frame, stores it as `profile.center`, and `GameBase.start()` loads it (default `{0, 0.25}` for profiles saved before this existed), so games place targets around the same point the envelope was measured from and two sessions are comparable. The sweep screen is deliberately sparse — it used to carry a dashed arm-length circle, a square framing it, sixteen large direction dots, a seven-blob pacer running most of the sweep, a heavy glowing envelope and three separate marks on the hand, which is a lot of scenery over a measurement. What is left: a start-point dot, small direction dots that hug the patient's own traced shape (the only "what have I not covered" signal), the painted envelope drawn thin, a short pacer firefly that fades once they are clearly going round on their own, and the red hand cursor. **No preset guide circle** — the arm-length boundary is implied by the pacer and the hold targets rather than drawn three times. `CENTER` is mutated in place; `samplePos`/`fromCenter` read it live.

**Shoulder width is the ruler, arm length is the reach.** SW normalizes camera distance, but the AL/SW ratio varies ~1.2-1.7 between people and SW is a *projected* width that shrinks a few percent when the trunk turns — so "0.9 SW" is a different fraction of reach for different patients and different postures. `tracker.armLenSW(side)` keeps arm length (shoulder→elbow→wrist summed, bend-invariant) as a **decaying session max**; the assessment stores it as `profile.armLenSW` and `GameBase.start()` sets `armScale = clamp(live/stored, 0.8..1.25)`, which `envAt()` applies — so `rangeScale` means the same fraction of *this* reach every session. Sitting closer or further also has to move the frame's **scale**: the origin stays locked (a reach must never drag the world) but `_ingest` re-snaps `frame.sw` after `SCALE_HOLD` ms of >`SCALE_DRIFT` change **confirmed by the torso length moving the same way** — biacromial width alone shrinks on yaw, torso length barely does, so a turn can't be mistaken for a distance change.

**Who the tracker follows.** MediaPipe runs at `numPoses: 3` on purpose: asking for one body means the model silently hands over whoever it scored highest *this frame*, so a therapist or a second patient can become "the" body mid-round. `_pickBody`/`_feature` keep our own lock instead — cost = per-frame midpoint displacement + shoulder-width mismatch + build-ratio (torso/SW) mismatch, gated at `LOCK_GATE`; no acceptable match means **pause, never swap**, and only after `LOCK_GRACE` ms is a new (most central) person accepted. `relock()` forgets it — `finishLogin` calls it. `tracker.peopleSeen` is the count, for staff diagnostics. **Click to follow on a webcam too (Oct 2026, by request):** `_pickBody` publishes everyone it saw as `tracker.people` in the bridge's shape (`{id, x unmirrored, y, sw, seat}`), so `drawPeopleMarkers` rings them on both camera paths; a click calls `selectPerson(id, 0, at)`, which on the webcam queues `pick` and `_pickFrom` takes the body nearest the click on the next frame and **pins** its build (`tracker.pinned`): a pinned person survives `relock()` (the pick is made on the first screen, before the name; `relock(true)` lets go), and after an absence is re-acquired by build match (or as the only body), never as whoever is most central. This is a build signature, not a face: face recognition would mean an embedding model and storing patient biometrics for no gain in a room with two or three people. The ZED path does the same job in the bridge (play volume + build signature, above).

Rendering and hit-testing go through the tracker's **stable frame** (`tracker.frame`): a snapshot of the body anchor that stays fully locked for the whole round (so reaches/sway/jitter never move the world) and re-snaps only at `setBaseline()` (round start, after a relocation pause). The live anchors are for compensation/relocation signals only.

The tracker keeps the body anchor on two time scales: a slow filter (targets follow legitimate repositioning) and a fast filter. Fast-vs-slow divergence is the **compensation signal** consumed by `coach.js` (trunk lean / shoulder hike / rotation → amber skeleton, world dim, spoken cue, logged event). Large sustained change triggers `relocated()` → graceful pause + re-baseline in the game loop.

### Assessment → profile → difficulty

**The assessment (Sep 2026 rebuild): one arm, two steps, about four minutes.** `assessment.js` measures the arm chosen at login and nothing else. **Once a day** (Sep 2026, by request): the select screen locks the games until the arm has a profile dated today (`measuredToday` in `main.js`) and locks the assessment card once it has ("Measured today"); `startAssessment` refuses a second one the same day unless called with `override: true`, which only the staff drawer and the therapist profile screen pass. The drawn demonstrator (`_drawDemo`, figure style) fills about 55% of the screen height since Sep 2026 (it was too small to follow). Flow: hold still (the **wrist** inside a 6 cm circle for 1.5 s, `STILL_R`; the wrist is the scored point on every camera path, never the palm, whose ZED stand-in points lag and jump; **one circle only** — `drawBody` is called with `hands: false` so the skeleton's palm discs never put a second ring on the hand, and while measuring the red wrist cursor is the only mark) → **demo** → 3-2-1 → **step 1: two circles**, one each way, each shown first by the demonstrator going that way, then a **lift**, also shown first → **step 2: five targets**. The demonstrator (`_drawDemo`, `_startDemo`) is a **seated** figure mirrored to the assessed arm. There is **no squeeze-calibration step** (removed Sep 2026; `profile.curlCal` is null and the tracker self-calibrates grasp).

- **Circles.** "Make a big circle, as big as you can, all the way round", then "now the other way round". A lap is a full turn of *net* signed angle about the centre (`lapAngle`), so wobbling cannot finish it early or stop it finishing; lap 1 accepts either sense, lap 2 wants the opposite and gets one gentle reminder (`LAP_NUDGE_ANGLE`) if it sets off the same way; `LAP_MAX_MS` (40 s) is the last word. `profile.laps[]` records direction, seconds and whether each closed; `loopSeconds` (the DDA speed input) is the mean completed lap. A pacer firefly runs the wanted way for the first `PACER_UNTIL` of each lap, and lap 2 draws a curved arrow (`_drawTurnArrow`). No targets on the way round on purpose: chasing one mid-circle distorts the shape.
- **Lift.** "Lift your arm straight up, as high as you can, then bring it back down": shoulder flexion and extension asked for directly. The first `LIFT_BASE_MS` gives the starting elevation, the peak is tracked, and the step ends when the arm has come back to within `LIFT_RETURN` of the rise (or `LIFT_MAX_MS`). `profile.lift = {startDeg, peakDeg, rangeDeg, returned, seconds}`; `arcMinDeg/arcMaxDeg` still come from every sample of every phase.
- **Targets.** Five directions (`TARGETS`: down-out −45°, out 10°, up-out 65°, up-across 125°, across 180°, mirrored per arm by `_extTheta`) placed at `TARGET_FRAC` (0.85) of the reach the circles measured in that direction (the wedge's own unfloored `envRaw` value; **a direction the wrist never visited turns the ask to the nearest visited wedge** (Sep 2026: borrowing 0.6 of the best reach put that target outside the painted shape), so every target is inside the workspace by construction), never past the arm-length boundary (`_demoR × EXT_REACH`) and never off the stage (`_screenR`) — **always inside the traced shape**, frozen in `_buildTargets` so nothing moves while they reach. Per target: up to `TARGET_REACH_MS` (10 s) to arrive within `cap`, then a `GRASP_MS` (7 s since Oct 2026) window for the **grasp check** (Oct 2026, by request): one short ask at a time (`e.gstep`: a hand that arrives open is asked to squeeze then open; one that arrives closed, `preClosed`, to open first, then squeeze, then open, so both state changes are seen), each spoken once, a state counted only after it has held `GRASP_HOLD_MS` (300 ms), drawn as one big hand (✋ / ✊, 8.5% of the screen height) over the target with the word under it and "we see: open / closed" below the target so a squeeze the camera is not seeing is visible rather than guessed. Reaching is the pass/fail and grasping never is. Results go in `profile.extremes[]` (kept under the old name because the profile map, the compare screen and the email read it: `{key, deg, reached, frac, reachSW, askSW, anatSW, askFrac, fracAnat, timeMs, holdMs, stability, squeeze, release, preClosed, graspOk}`), with `grasp[]`, `reachablePositions` and `graspPositions` as views of it.

**The figure-flow stage is zoomed to the person (Oct 2026, by request: the camera is often a few metres back):** `_zoomOf` maps a window about the body centre of the arm's length plus `ZOOM_PAD_SW` (0.5 SW) onto the stage (only in, never out, capped at `ZOOM_MAX` 2.5, eased by `ZOOM_EASE`), applied as one canvas transform to the picture and skeleton in `_loop` and to the shape, targets and cursor in `_draw` (text sizes divided by the zoom so they stay put; the coach dock is drawn outside it); `_screenR` keeps targets inside the zoomed view (`_viewRect`); the window is clamped so the zoomed picture always covers the stage (no dark band when the body centre sits low in the picture). Because the zoom is proportional to the inverse of the live pixels-per-SW, a target's drawn size and the skeleton's stay the same on screen as the person moves nearer or farther, while every size and capture radius stays in SW underneath. The video stage has its own crop (`_drawPersonPanel`). **Everything is measured about the body centre** — `CENTER` is set to `{0, 0}`, the shoulder midpoint that is the origin of the SW frame, at settle — not about the resting hand as before. That is what makes two sessions comparable, and `profile.center` is stored as `{0, 0}` (`profile.reference: "body-centre"`) so the games place targets from the same envelope about the same point. The envelope is star-shaped from there (the arm's reachable disc contains the shoulder midpoint), and "across" in the quadrant names is genuinely across the midline.

### Games

`engine.js` exports `GameBase`: round loop with pause handling, `samplePos()` (envelope-bounded AND clamped on-screen via margins, staying body-anchored), `hit()`/`miss()` accounting, particle bursts, the always-drawn arm skeleton + hand cursor with capture-radius ring, and the "therapist voice" (`say()`, `_feedbackTick()` — spoken praise/tips, rate-limited).


**Catch Together** (`rgs`, **disabled since Sep 2026**: every game is for the one arm chosen at setup and this one is bimanual by definition — re-enable by deleting the flag) is a rebuild of the Rehabilitation Gaming System's own task (`Unity-simple-RGS-game`, and the spheroids paper `06091665.pdf`): balls approach in depth and are caught with **both hands cupped together** — a single hand cannot catch, and that coupling is the therapy — then carried to a colour-matched trough. Three graded stages (catch → carry → sort) stand in for RGS's four conditions, with the original's **wait-vs-continuous** pacing as a per-stage flag (one ball at a time is the difference between a task and a queue for a slow reacher). Lanes and troughs sit inside the measured envelope, which the original's fixed world positions did not. RGS's **observation condition** (the game plays itself while the patient watches) is deliberately **not** included: it is well-founded but it is a different intervention with its own consent conversation, not a difficulty stage, and a rehab game that takes the controls away mid-session reads as a freeze. `bothArms` must be true for it (set in `main.js#startGame`), and stage progression mirrors Drift's.

**Cloud Slingshot** (`sling`) is the Angry Birds mechanic rebuilt for the arm: reach the pouch, close the hand, pull back, hold the stretch, open to fire at towers of dark clouds. The pull *is* the exercise — a graded, held, eccentric reach ending in a release. **Power is normalised to the patient's own reach** (`_maxPull` = `rangeScale × envAt` in the pull direction), not to screen pixels as the reference does — with a fixed factor the game would be literally unwinnable for the people it is for. Simulated: the tower is reachable from ~40% of their reach, and a weaker shot still flies and lands visibly short rather than doing nothing. Release is hand-open, with **holding the stretch still for `SL_HOLD_MS`** as the no-grasp path — and that hold is worth asking for in its own right. `meanPullFrac`/`bestPullFrac` are logged: how deep into their own range each pull went is the number this game exists to move. Physics is ~200 lines written here; the reference carries Phaser + p2 (about 3 MB) to do the same job.

**Connect the Dots** (`dots`) is the point-to-point game: hold on dot 1, then 2, then 3, and a line follows until a picture closes. Levels add dots (10 → 44) and shrink the capture radius together — the same drawing asked for more precisely, like the paper puzzles that go 1-10 / 1-30 / 1-150. `dotsFromOutline` puts **every outline vertex on a dot first** and spends the spare dots on the longest edges: even arc-length spacing walks straight past corners, and a star resampled to 8 even points stops looking like a star. Dots are laid in the patient's own envelope and each one is pulled radially in to `spread × envAt(th)` if the picture's box would push it past their reach (the corners of any box sit further out than its axes), so a picture is never partly unreachable. Only the NEXT dot is lit and numbered — lighting them all is what makes a paper puzzle confusing; here there is always exactly one thing to go to. Squeeze is a shortcut over the dwell, never a requirement. Level banked via `store.getLevel/setLevel("dotsLevel")`.
**Memory Pairs** (`pairs`, Sep 2026, by request, from `mockups/memory-game-master.zip`) is the card-matching Memory game rebuilt for the arm: a grid of face-down cards, hold the hand on one to turn it (sticky dwell, never a click or a squeeze, so every turn is a reach and nothing is asked of the hand), a matching pair stays up, a mismatch turns back after `PAIR_SHOW_MS`. The grid is laid inside the measured envelope the way Connect the Dots lays its dots (a box on the axes the arm has, each card pulled radially in to `spread × envAt`, kept on screen), **then frozen in screen pixels for the whole board** (positions, `cardW/cardH`, `radiusPx`; hit-testing at `palmPx`) so a tracking re-snap never shifts a board the patient is trying to remember (Sep 2026, by request after the first play), and `PAIR_LEVELS` is the ladder (2×2 → 5×4, capture radius shrinking, spread widening; banked per patient as `pairsLevel`, up a level on every cleared board). Every board opens with a **peek** (all cards face up for `PAIR_PEEK_BASE + PAIR_PEEK_MS × pairs`, a thin bar showing the time left), so it is study-then-recall rather than guessing. A mismatch is counted as `wrongTurns` in the round record and **never** fed to `miss()`: the DDA reads motor performance and a forgotten card is not a motor error. The faces are drawn glyphs (`drawGlyph`: star, moon, heart, boat, fish, house, sun, cloud, lantern, anchor), not the mockup's emoji, because a clinic PC may render none. Per round: `pairsFound`, `turns`, `wrongTurns`, `boardsCleared`, `cards`.
**Lantern** (`candles`, Oct 2026; the id `lantern` already belonged to the disabled grasp-and-carry `LanternRelease`) is **the Lamplighter of Lumen, rebuilt from `mockups/lantern-game (1).zip`** (Oct 2026, by request: Mira the lamplighter, Pip the owl, the Night Moth; `class Candles` in `games.js`, the constants prefixed `LUMEN_`). The loop is the mockup's: hold the hand on the **basket** (a sticky dwell, `A11Y.dwellMs`) to take a candle, a **lantern** appears (hidden until the candle is taken, so the first move out is a reaction time, `rt`), carry the flame to it (the candle burns down while it travels, `burnMax = max(8, 3 × params.lifetime)` s, and stops burning while held inside the lantern), light it, back to the basket. The basket moves left / centre / right between candles in a balanced shuffle (`_nextHome`, `LUMEN_BASKET_SIDE`) while the lanterns stay fixed. **Twenty-three levels in six stages** (`LUMEN_LEVELS` / `LUMEN_STAGES`, the mockup's ladder verbatim, `CANDLE_MAX` exported): Reach (1-5: more positions, smaller lanterns), **Reach and hold, both hands** (6-10; **bimanual since Oct 2026, by request**: the candle comes out of the basket *unlit*; the trained hand carries it to the lantern and keeps it there, then the other hand reaches to the **fire**, a brazier on its own side where the keeping hand's stand would be (`this.fire`, `_drawFire`, a 600 ms dwell to take the flame, `matchLit`), brings the match to the lantern, and with both hands held there the ring fills over `hold` seconds; `c.step` candle → fire → bring, `tFire` logged; the flame hand slipping out empties the ring after `LUMEN_HOLD_GRACE` like the candle hand; the drawer's keeping-hand modes stand down in this stage and the basket stays central; a `LUMEN_HOLD_GRACE` 400 ms wobble forgiven, longer counts as a `holdBreak`), Colour match (11-13: a decoy; the candle's colour **and glyph** say which, `LUMEN_COLORS`), Number trail (14-16: light in order, level 16 alternates 1 A 2 B; every finished trail reveals one of eight `LUMEN_CONSTELLATIONS` in the top-right box for the Star Atlas), the Night Moth (17-19: a red no-go circle on the path, `_placeMoth`, with a green dotted way round shown through level 17 and the first candles of the others) and Moving lights (20-23: the lantern sweeps ±`LUMEN_MOVE_AMP` about its angle and ±18% in and out along a dotted track; from 22 the basket drifts too; **the rate is capped so the lantern's peak speed suits the patient**, `_moveSpeed`: `LUMEN_MOVE_PEAK / params.lifetime` disc units/s, because the mockup's cycles per second were for a mouse). ### Accessibility (a11y.js)

`a11y.js` holds the live `A11Y` state (mirrored from the patient's saved settings on login and on every drawer change), `applySettings`, and `speakLine` — the single speech path (rate, patient-set voice volume, optional on-screen caption in `#caption`). All app speech goes through it (`main.js speak`, `GameBase._speak`, `coach.js`); in-game `say()` and stories skip the caption because `#cue`/`#prompt` already show the text. Per-patient settings live in `store.getSettings/saveSettings` (captions, dwell time, capture-radius scale, squeeze ease → `tracker.setSqueezeEase`, high contrast, calm motion, text scale, practice mode, visual-field flag, per-bus volumes) and are edited in the staff drawer's Comfort section. Engine-level behaviors: `samplePos` respects the visual-field policy (comfort = bias spawns to the intact side; scan = train the cut side — hemianopia is independent of the reach envelope), `glow()` adds dark rims in high-contrast mode, `burst()` softens under calm motion, `miss()` is a no-op in practice mode (and `main.js#onRoundEnd` skips logging/DDA), the welcome skeleton goes dashed when not framed (amber/sage is a red-green confusion pair — never signal by that hue pair alone), and every 4th round (or a compensation spike) triggers a spoken rest suggestion. `audio.js` has `musicBus`/`fxBus` gains (`setVolumes`).
