# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

STRIVE (formerly Star Harbor / "Rehab Suite") — a webcam-based upper-limb rehabilitation game suite for stroke patients, developed by Synapse Lab, Shirley Ryan AbilityLab. UI copy convention: no em dashes in patient-facing text. Plain static site: vanilla JS ES modules, no build step, no dependencies to install, no tests or linter. MediaPipe Pose is loaded from CDN at runtime (internet required on first load). Design decisions are grounded in two rehab papers (CFI framework, Rehabilitation Gaming System) — README.md has a table mapping paper concepts to code; SPEC.md and DESIGN_BRIEF.md hold the full spec and visual design language.

## Run

```
python -m http.server 8321
```

then open `http://localhost:8321` (or double-click `start_game.bat`). A server is required — camera access is blocked on `file://` pages. Testing requires a webcam and allowing camera access; data persists in the browser's localStorage under the key `rehabsuite-v1` (do not rename the key — it would orphan patient data).

**ZED 2 (optional):** `python tools/zed_bridge.py` runs the ZED SDK's depth-based body tracking (BODY_38) and streams it on `localhost:8322` (`/status`, `/stream` SSE skeletons in MediaPipe 33-landmark layout, `/video.mjpg` mirror preview). Each skeleton carries `lm` (normalized 2D) **and `lm3` (the same joints in metres, camera frame: x right, y down, z forward)** — the depth channel `tracker._ingest3`/`hand3(side)`/`has3D` expose and the assessment turns into a real workspace volume; a webcam has no depth, so the volume is simply absent there rather than estimated. With the staff-drawer "Camera source" setting on Auto (the default, stored device-level in localStorage `strive-cam-source`), `tracker.js` probes the bridge at boot and uses the ZED when it's up, webcam + MediaPipe otherwise; the source is chosen once at boot, so changing the setting reloads. In ZED mode **grasp comes from the MediaPipe 21-point hand model run in the bridge** (Sep 2026, by request, the way `zed_track.py` does it): `HandWorker` in `zed_bridge.py` is a thread of its own with one VIDEO-mode landmarker per side, fed every 2nd frame a square crop of the **full-resolution** left image about each of seat 0's wrists (`hand_crops`: nudged towards the fingertips, 150-460 px sized by the shoulder width in pixels; the crop is what makes a hand at 4 m detectable at all), measuring the curl on the model's **world landmarks** (`mp_curl`, no foreshortening), and the freshest result rides in the payload as `hands: [{side, pts, curl}]` with the 21 points levelled for camera roll and normalised like `lm` (`--hands off` disables; `/status` says `hand_model` and `hand_ms`; the model file is the shared gitignored `tools/models/hand_landmarker.task`, downloaded on first use). `tracker._startZed` feeds them to `_ingestHands` (proximity matching, unchanged) with the curl, which `handCurl` returns in preference to the image-point ratio; the curl band now has `zed_track.py`'s hardening too (`CURL_CAL_GROW`, `CURL_CAL_MAX_RANGE`, `CURL_PLAUSIBLE`). Only when the bridge reports no hand model does the browser run the model itself on the MJPEG preview (`_loadHands` in `init`, the loop in `_startZed`), a weak fallback at ward distances; BODY_38's own fingertip heuristic is the last resort. **Camera picture (Oct 2026, by request):** the bridge and `zed_track.py` open the ZED at **HD2K, 2208×1242, 15 fps** (`PROFILES`; `--res HD2K|HD1080|HD720|VGA` and `--fps` override, `pick_fps` clamps the rate to what the size supports, `RES_FPS`, since HD2K only does 15): the full sensor makes a hand at 4 m big enough for the hand model, and at 60 fps the sensor could never expose longer than ~16 ms, so a ward without studio light came out dark, flat and noisy. The hand crop band (150-460 px) was tuned on a 1280-wide picture and scales with the width (`REF_WIDTH`), and the hand model and the MJPEG preview take every frame at 15 fps (every 2nd at 30) so neither loses rate; the preview is still downscaled to `--preview-width` (640). Both also push the SDK's picture settings after open (`apply_picture`: brightness 6, contrast 5, gamma 9 of the SDK's 4/4/8 defaults; `--brightness/--contrast/--gamma`, and `--exposure fixed --exposure-val N --gain N` to leave auto exposure) and print what the camera reports back — the ZED's ISP is tuned for stereo matching and, unlike a webcam driver, lifts nothing on its own. **Camera roll is corrected in the bridge (Sep 2026, by request):** a ZED clamped a few degrees off level tilted the trunk the posture coach watches and the y-up frame the assessment measures in, so `Tilt` reads the IMU's accelerometer each frame (`get_sensors_data`, specific force in the image frame, sign-normalised so y is positive), takes the roll about the optical axis as `atan2(gx, gy)`, smooths it slowly, and `body_to_lm` turns every 2D keypoint about the image centre by that angle (`level_px`) while the MJPEG preview gets the same turn with `cv2.warpAffine`, so the skeleton, the people markers and the picture stay in step; `/status` reports `tilt_deg` (applied) and `tilt_raw_deg` (measured). `--tilt auto` (default) | `off` | a fixed angle in degrees; a dead band of 0.4° leaves a level camera untouched and anything past 30° is refused. Only roll is corrected (pitch and yaw do not tilt a person in the picture), and the 3D `lm3` is left alone because positional tracking runs with the SDK's default gravity-aligned world origin. **Distance is lenient on purpose:** patients are in a ward bed or chair 5-15 ft away, so `--max-range` and `--play-far` default to 5 m, `--play-width` to 4 m, and the welcome screen's `framingMessage` only asks them closer below a 0.03-frame shoulder width (about 5 m on the ZED's lens) and accepts a body anywhere in the middle 70% of the picture; seeing them is what matters, SW units make the distance irrelevant downstream. Requires ZED SDK + pyzed on the machine; the game itself never needs it.

**Two players (ZED only):** `python tools/zed_bridge.py --bodies 2` streams two seats. Seats are assigned by **where people stand** (seat 0 = left-most in the image at lock time), then followed by ZED tracking id — never by confidence, which is what would hand a paddle to the other player mid-rally. A seat is held through `--seat-grace` seconds of occlusion, then re-seats to the nearest unclaimed body; `GET /relock` forces a re-seat. Who is a candidate at all is decided **first by where they stand**: `in_play()` admits only bodies inside the play volume (`--play-near`/`--play-far` metres deep, `--play-width` metres wide about the camera axis; defaults 0.6-5 m x 4 m since Sep 2026, for ward beds 5-15 ft away), so a therapist standing behind the patient is never in the running whatever the detector scores. Tracking ids do not survive somebody leaving the room, so each seat also remembers a **build signature** — biacromial width, torso length and height in metres from depth, EMA-smoothed, matched within `--sig-tol` when a free seat is refilled (`build_signature`/`sig_distance`). That is deliberately **not** face recognition: no extra model, no biometric stored, and enough to tell apart the two or three people actually in a therapy room. The payload keeps seat 0 as the top-level `lm`/`lm3`/`shm` (the single-player game reads it unchanged) and adds `bodies: [{seat, id, lm, lm3, shm}]` **and `people: [{id, x, y, sw, z, seat, play}]`** — everyone in view, seated or not, at the shoulder midpoint in normalized image coordinates. **Staff pick the patient by clicking (Sep 2026):** with two or more people in view the welcome screen draws a ring on each (sage = followed, amber dashed = *Click to follow*, `drawPeopleMarkers` in `main.js`) and the staff drawer lists them as buttons (`renderPeople`, with left/middle/right and distance); a click calls `tracker.selectPerson(id)` → `GET /select?id=N[&seat=S]` → `Seats.pin`, which makes the seat **sticky**: it follows that tracking id, bypasses the play volume, relearns the build signature from that person, and once they are gone refills only by signature match or when exactly one person is in view — never by who stands left-most, so a visitor cannot take the patient's seat. `?clear=1` lets a seat float again; `/relock` clears everything. `tracker.js` routes seat 1 into `_ingestSecond` — a deliberately thin second body (shoulders, wrists, trunk only) exposing `armAngle2(side)`/`p2TrackingOk`, touching none of `pts`/`anchor`/`frame`, so compensation, grasp, relocation and the DDA can never be moved by a second person in the room. Pong's `duo` mode uses it: each player's arm side is chosen once in `renderDuoSetup` (`main.js`) and fixed for the round, player 2 is a saved patient whose own `arcMinDeg/arcMaxDeg` drives their paddle (guest = default arc), an untracked player 2's paddle **holds position** rather than snapping to center (a snap would gift a point), the round-1 tutorial is skipped (it is a solo speed measurement), and `score.ai` doubles as player 2's tally. The mode needs the ZED: one webcam pose model reports a single body, so the tile explains itself instead of failing mid-round.

Two ZED tools sit beside the bridge, both reusing its `PROFILES` and `resolve_indexes()`, plus `tools/zed_common.py` (the shared `Readout` that turns one BODY_38 skeleton into the overlay and the numbers — so the two tools can never report different values for the same pose; it imports opencv lazily so the diagnostic can still run and *report* a missing opencv), so they test the path the game actually uses (stop the bridge first — one process at a time can hold the camera): `python tools/zed_test.py` is the staged diagnostic (pyzed import, CUDA GPU via `nvidia-smi`, device enumerated, open, measured fps, depth validity, BODY_38 detection rate, biacromial width, and whether the landmarks the game needs actually fill in), exit 0 when every stage passes, and during the body stage it shows the RGB feed with the skeleton and the live tracking numbers (`--no-preview` for headless); `python tools/zed_view.py` is the live window (skeleton, per-joint XYZ in the SDK camera frame, the same points in SW units with a 1-SW ring, 3D elbow flexion, `armAngle` elevation, and the grasp state replayed with `tracker.js`'s own `GRIP_*` constants so it agrees with the game). Run them from Windows Python, not WSL — WSL cannot see the camera without USB forwarding. The ZED needs no manual calibration (factory-calibrated, SDK self-calibrates at open); the calibration that matters is the in-game assessment, plus letting the fingertip grip envelope widen by opening and squeezing a few times.

**`tools/zed_track.py` (Sep 2026, step one of the rebuild)** is a single-file realtime viewer with no imports from the other tools, run with `py -3.12` (the only Windows Python with pyzed). It shows the ZED's **left RGB eye** (mirrored) and nothing else; every number comes from the SDK's 3D body tracking (BODY_38, model FAST / MEDIUM / ACCURATE, switchable live from an on-screen dropdown or `n`). Per arm: shoulder/elbow/wrist/hand XYZ in metres (camera frame) and the hand from the shoulder in the body's own frame (out / up / forward, cm), **elbow flexion** (0 = straight, computed in 3D), and the shoulder as the ISB pair of **elevation** (0 = arm down, 180 = overhead) in a **plane of elevation** (0 = out to the side, 90 = straight ahead, negative = behind) named with the therapist's word (abduction / scaption / flexion / across / extension). Projected flexion/abduction angles are deliberately not shown: they flip between +180 and -180 once the arm is above horizontal in the other plane, so a real posture (arm abducted overhead) would read as noise. The body frame is rebuilt from shoulders, hips and nose, so the angles do not change when the patient sits at an angle to the camera (checked by yawing a synthetic body). **Grasp** defaults to the **MediaPipe 21-point hand model** (`tools/models/hand_landmarker.task`, downloaded on first use, gitignored) run on a square crop of the RGB frame around each ZED wrist, one VIDEO-mode landmarker per side so the two hands are never confused, about 9 ms per crop on the CPU; the curl is `tracker.js`'s `handCurl` (mean fingertip-to-wrist over palm length, about 2 open and 1 for a fist) measured on MediaPipe's **world landmarks** (metric, hand-centred 3D) so a hand turned edge-on or pointed at the lens does not foreshorten into a fist, then run through the same `CURL_*` band and self-calibration, with one hardening the game does not have yet: the band may only **grow** by `CURL_CAL_GROW` (0.02) per frame, its span is capped at `CURL_CAL_MAX_RANGE` (1.4) and values outside `CURL_PLAUSIBLE` are ignored, because one wild frame lifting `hi` to 3.0 put "open" out of a real hand's reach for minutes and the right hand read CLOSED for ever after (the first live session showed exactly that). The band is drawn under each arm panel (observed range, the close and open thresholds, the hand's current curl) so a calibration problem is visible rather than inferred. The ZED's own four BODY_38 hand points remain selectable (dropdown or `g`) but are too coarse to call open/close reliably. With more than one person in view every body gets a thin grey skeleton and a *click to track* label; the chosen person is followed by the SDK's tracking id (click, Tab, `0` clears, `--person ID`), never by per-frame confidence, and if they drop out the viewer **waits** rather than swapping to whoever is left, adopting a lone person only after 3 s because the SDK hands a returning person a fresh id. `--demo` runs two figures built from known angles with no camera, `--snapshot x.png` renders one frame and exits, `--log arm.csv` appends every frame's positions, angles, grasp state and which models produced them, and keys pick the arm (1/2/3), mirror (m), labels (x) and reset the grasp band (c).

**Therapist contact (optional):** `python tools/mail_bridge.py` runs a local SMTP relay on `localhost:8323` (`GET /status`, `POST /send {kind, subject, body}`). A static page cannot send email, and the alternatives both fail this project — a third-party email API would need its key embedded in a public page and would route patient data through somebody else's server, while `mailto:` alone only opens a client and waits for a human. So mail goes the way body tracking does: through a local service, with the credential in gitignored `tools/mail_config.json` (copy `mail_config.example.json`; Gmail needs an **app password**) or `STRIVE_SMTP_*` env vars, read only by that process and never by the browser. `python tools/mail_bridge.py --test` sends one message and exits, to check setup without opening the game. `js/mail.js` probes it at boot and the staff drawer's **Therapist contact** section gets three buttons — *Send test email* (connectivity + diagnostics), *Report a problem* (a typed description plus `diagnostics()`: camera source, tracking state, people seen, hand model, arm lengths, browser), *Email progress* (`progressReport()`: the arm's assessment, workspace area/volume/coverage/quadrants, edges reached, grasp, the last 10 rounds, compensation). With the relay down every button falls back to a prefilled `mailto:` so nothing dead-ends. **Two things send without a staff press (Sep 2026, by request):** a **login notice** (`notifyLogin`: participant, arm, round count, diagnostics) goes out when a named participant logs in, and the patient-facing **Help** button (`#btn-help`, every screen but login, rate-limited to one a minute) sends a help request with diagnostics and says "Help is on the way". The login notice goes only through the relay — with no relay it sends nothing rather than opening a mail window on a patient. **Session reminders** (Sep 2026): the create step (and the staff drawer) take an optional email, a time and days (off / daily / weekdays) → `store.setContact` → `mail.setReminder` posts it to the relay's `POST /reminder`; the relay keeps `tools/reminders.json` (gitignored: addresses) and a daemon thread sends "Time for your therapy session" to the participant at that time, once a day (`lastSent`), so it works with the page closed. **Update by email** (Sep 2026): a sender on the config's `askers` list emails the STRIVE account with subject `STRIVE update <name>` (or `STRIVE update` for the list); the relay's `inbox_loop` polls the inbox over IMAP every 60 s and replies with the report and the JSON export from the last **snapshot** the game pushed (`mail.pushSnapshot` → `POST /snapshot` → `tools/snapshots/<name>.json`, gitignored; pushed by `main.js#snapshot` at login, after every round and after an assessment). Anyone not on the list is ignored and logged. Nothing sends on round end except that snapshot to the local relay. **Play time** is logged per local day (`store.logPlaytime`/`playtime`: ms, rounds, assessments; each round record now carries `seconds`), shown on the profile subtitle and in the progress email (`playtimeLines`).

## Architecture

Data flow: webcam → MediaPipe Pose (`tracker.js`) → body-relative coordinates → assessment (`assessment.js`) → per-arm profile → games (`games.js` on `engine.js`) → round stats → DDA (`dda.js`) → updated params → localStorage (`storage.js`). `main.js` is the app shell that wires screens, rounds, and the staff/therapist UI together.

### The coordinate system (everything depends on this)

All game/assessment positions are in **shoulder-width units (SW) relative to the shoulder midpoint, y-up** — camera-distance independent and comparable across sessions. `tracker.js` owns the conversions: `handRel(side)` (hand in SW), `relToPx`/`pxToRel` (SW ↔ canvas pixels), `pxPerSW(canvas)`, `armAngle(side)` (arm elevation in degrees vs the trunk axis, 0 = down, 180 = overhead), plus `palm(side)` and `handClosed(side)` (grasp detection — used by Harbor Crates grab/release, Pong skill shots, the assessment squeeze, and the palm disc on the skeleton). Grasp runs two-tier: a dedicated **Hand Landmarker** (21 pts/hand, every 2nd frame, matched to pose wrists by proximity) gives finger-curl via `handCurl(side)`, with **self-calibrating per-person thresholds** (`curlCal` envelope: once enough curl range is seen, "closed" = 35% into that patient's own range, so a partial squeeze still registers; fixed 1.25/1.55 hysteresis until then); if it has no fresh detection, a self-calibrating pose-fingertip heuristic (`grip(side)`) is the fallback. Video coordinates are mirrored (`x = 1 - lm.x`) so the game acts like a mirror. A **stereo webcam** (a ZED plugged in as plain UVC, with no bridge running) delivers one double-wide `left eye | right eye` frame; `tracker.isStereo` (aspect ≥ `STEREO_RATIO` 2.6) detects it and everything reads `srcW`/`srcH` instead of `videoWidth/Height` — `_detectSource()` feeds both models a left-eye crop and `drawVideoMirror` blits only that half, so the patient never sees the room twice and MediaPipe never searches a squashed 2:1 image.

Envelope-based targets and the assessment circle are centered on `CENTER` (exported from `engine.js`) — **the body centre**: the assessment sets it to `{0, 0}`, the shoulder midpoint that is the origin of the SW frame, stores it as `profile.center`, and `GameBase.start()` loads it (default `{0, 0.25}` for profiles saved before this existed), so games place targets around the same point the envelope was measured from and two sessions are comparable. The sweep screen is deliberately sparse — it used to carry a dashed arm-length circle, a square framing it, sixteen large direction dots, a seven-blob pacer running most of the sweep, a heavy glowing envelope and three separate marks on the hand, which is a lot of scenery over a measurement. What is left: a start-point dot, small direction dots that hug the patient's own traced shape (the only "what have I not covered" signal), the painted envelope drawn thin, a short pacer firefly that fades once they are clearly going round on their own, and the red hand cursor. **No preset guide circle** — the arm-length boundary is implied by the pacer and the hold targets rather than drawn three times. `CENTER` is mutated in place; `samplePos`/`fromCenter` read it live.

**Shoulder width is the ruler, arm length is the reach.** SW normalizes camera distance, but the AL/SW ratio varies ~1.2-1.7 between people and SW is a *projected* width that shrinks a few percent when the trunk turns — so "0.9 SW" is a different fraction of reach for different patients and different postures. `tracker.armLenSW(side)` keeps arm length (shoulder→elbow→wrist summed, bend-invariant) as a **decaying session max**; the assessment stores it as `profile.armLenSW` and `GameBase.start()` sets `armScale = clamp(live/stored, 0.8..1.25)`, which `envAt()` applies — so `rangeScale` means the same fraction of *this* reach every session. Sitting closer or further also has to move the frame's **scale**: the origin stays locked (a reach must never drag the world) but `_ingest` re-snaps `frame.sw` after `SCALE_HOLD` ms of >`SCALE_DRIFT` change **confirmed by the torso length moving the same way** — biacromial width alone shrinks on yaw, torso length barely does, so a turn can't be mistaken for a distance change.

**Who the tracker follows.** MediaPipe runs at `numPoses: 3` on purpose: asking for one body means the model silently hands over whoever it scored highest *this frame*, so a therapist or a second patient can become "the" body mid-round. `_pickBody`/`_feature` keep our own lock instead — cost = per-frame midpoint displacement + shoulder-width mismatch + build-ratio (torso/SW) mismatch, gated at `LOCK_GATE`; no acceptable match means **pause, never swap**, and only after `LOCK_GRACE` ms is a new (most central) person accepted. `relock()` forgets it — `loginAs` calls it. `tracker.peopleSeen` is the count, for staff diagnostics. This is a build signature, not a face: face recognition would mean an embedding model and storing patient biometrics for no gain in a room with two or three people. The ZED path does the same job in the bridge (play volume + build signature, above).

Rendering and hit-testing go through the tracker's **stable frame** (`tracker.frame`): a snapshot of the body anchor that stays fully locked for the whole round (so reaches/sway/jitter never move the world) and re-snaps only at `setBaseline()` (round start, after a relocation pause). The live anchors are for compensation/relocation signals only.

The tracker keeps the body anchor on two time scales: a slow filter (targets follow legitimate repositioning) and a fast filter. Fast-vs-slow divergence is the **compensation signal** consumed by `coach.js` (trunk lean / shoulder hike / rotation → amber skeleton, world dim, spoken cue, logged event). Large sustained change triggers `relocated()` → graceful pause + re-baseline in the game loop.

### Assessment → profile → difficulty

**The assessment (Sep 2026 rebuild): one arm, two steps, about four minutes.** `assessment.js` measures the arm chosen at login and nothing else. **Once a day** (Sep 2026, by request): the select screen locks the games until the arm has a profile dated today (`measuredToday` in `main.js`) and locks the assessment card once it has ("Measured today"); `startAssessment` refuses a second one the same day unless called with `override: true`, which only the staff drawer and the therapist profile screen pass. The drawn demonstrator (`_drawDemo`, figure style) fills about 55% of the screen height since Sep 2026 (it was too small to follow). Flow: hold still (the **wrist** inside a 6 cm circle for 1.5 s, `STILL_R`; the wrist is the scored point on every camera path, never the palm, whose ZED stand-in points lag and jump; **one circle only** — `drawBody` is called with `hands: false` so the skeleton's palm discs never put a second ring on the hand, and while measuring the red wrist cursor is the only mark) → **demo** → 3-2-1 → **step 1: two circles**, one each way, each shown first by the demonstrator going that way, then a **lift**, also shown first → **step 2: five targets**. The demonstrator (`_drawDemo`, `_startDemo`) is a **seated** figure mirrored to the assessed arm. There is **no squeeze-calibration step** (removed Sep 2026; `profile.curlCal` is null and the tracker self-calibrates grasp).

- **Circles.** "Make a big circle, as big as you can, all the way round", then "now the other way round". A lap is a full turn of *net* signed angle about the centre (`lapAngle`), so wobbling cannot finish it early or stop it finishing; lap 1 accepts either sense, lap 2 wants the opposite and gets one gentle reminder (`LAP_NUDGE_ANGLE`) if it sets off the same way; `LAP_MAX_MS` (40 s) is the last word. `profile.laps[]` records direction, seconds and whether each closed; `loopSeconds` (the DDA speed input) is the mean completed lap. A pacer firefly runs the wanted way for the first `PACER_UNTIL` of each lap, and lap 2 draws a curved arrow (`_drawTurnArrow`). No targets on the way round on purpose: chasing one mid-circle distorts the shape.
- **Lift.** "Lift your arm straight up, as high as you can, then bring it back down": shoulder flexion and extension asked for directly. The first `LIFT_BASE_MS` gives the starting elevation, the peak is tracked, and the step ends when the arm has come back to within `LIFT_RETURN` of the rise (or `LIFT_MAX_MS`). `profile.lift = {startDeg, peakDeg, rangeDeg, returned, seconds}`; `arcMinDeg/arcMaxDeg` still come from every sample of every phase.
- **Targets.** Five directions (`TARGETS`: down-out −45°, out 10°, up-out 65°, up-across 125°, across 180°, mirrored per arm by `_extTheta`) placed at `TARGET_FRAC` (0.85) of the reach the circles measured in that direction (the wedge's own unfloored `envRaw` value; **a direction the wrist never visited turns the ask to the nearest visited wedge** (Sep 2026: borrowing 0.6 of the best reach put that target outside the painted shape), so every target is inside the workspace by construction), never past the arm-length boundary (`_demoR × EXT_REACH`) and never off the stage (`_screenR`) — **always inside the traced shape**, frozen in `_buildTargets` so nothing moves while they reach. Per target: up to `TARGET_REACH_MS` (10 s) to arrive within `cap`, then a `GRASP_MS` (5 s) window to squeeze and open; a hand that arrives already closed has to open before a close counts (`preClosed`). Reaching is the pass/fail and grasping never is. Results go in `profile.extremes[]` (kept under the old name because the profile map, the compare screen and the email read it: `{key, deg, reached, frac, reachSW, askSW, anatSW, askFrac, fracAnat, timeMs, holdMs, stability, squeeze, release, preClosed, graspOk}`), with `grasp[]`, `reachablePositions` and `graspPositions` as views of it.

**Everything is measured about the body centre** — `CENTER` is set to `{0, 0}`, the shoulder midpoint that is the origin of the SW frame, at settle — not about the resting hand as before. That is what makes two sessions comparable, and `profile.center` is stored as `{0, 0}` (`profile.reference: "body-centre"`) so the games place targets from the same envelope about the same point. The envelope is star-shaped from there (the arm's reachable disc contains the shoulder midpoint), and "across" in the quadrant names is genuinely across the midline.

**Workspace readouts** (all from `envRaw`, the *unfloored* envelope — `envelope` is floored at `ENV_FLOOR` so games have somewhere to put targets, and area must not inherit that): `areaSW2` (shoelace over the 16 bin triangles), `coverage` = area / π·armLen², `quadrants` {upOut, upAcross, downAcross, downOut} named for the assessed arm, **`profile.rsa`** on the Bioniks Kinetigram device's planar Q1–Q4 scale (`method: "planar"`, `q5: null` because one front camera cannot see behind the trunk — absent, never zero), `rsaElbow` from the elbow's own orbit (the gap to `rsa` is the elbow's share), and — **ZED only** — `volumeM3` as a per-sector prism sum plus `depthRangeM`; `shoulderM` is stored so the cm conversion is self-contained. All of it surfaces on the therapist profile screen, in the progress email, and on `#screen-romcompare` (`renderRomCompare`, **reworked Sep 2026 by request: no table, no camera picture**). That screen is for the patient: a **plain dark stage** with a schematic figure at the body centre (`romFigure`: head, shoulders, trunk, the assessed shoulder marked amber) under today's envelope, last time's dashed, and the **ideal** dotted — the full circle of the arm's own length about the assessed shoulder, which is exactly what `coverage` is measured against; one **big number**, coverage as a percentage of that circle, with a `▲ n points more than last time` chip and one plain sentence; three tiles (lift in degrees of 180, targets reached, longest reach), one sentence each; and `romPlot`, a single-series SVG line of coverage per assessment day, 0/50/100 guides only, latest point bigger and labelled, so `store.saveProfile` now keeps **24** past profiles (was 6). Area, volume and RSA stay on the therapist profile screen and in the email. `store.saveProfile` keeps the replaced profile whole enough to compare against. Games must not spawn targets outside `rangeScale × envelope` — that is a clinical constraint, not a style choice.

Difficulty is stored **per game and per arm** (`store.getGameParams`/`saveGameParams`/`listGameParams`, shown on the therapist profile screen): the games make different demands, so a patient doing well at Pong is not necessarily ready for a harder Scratch Card. Ladder levels (`scratchLevel`, `dotsLevel`, `pongLevel`) are stored separately via `store.getLevel/setLevel`. `dda.js` defines the three difficulty params (`rangeScale`, `radius`, `lifetime`) with hard `LIMITS`, seeds them from the assessment (`initialParams`), and adjusts between rounds: hit rate >70% harder, <50% easier; when easing, `missFar` (misses beyond 70% of range demand) decides whether to reduce range demand vs grow radius/lifetime. `main.js` additionally holds difficulty steady if ≥3 compensation events occurred in the round.

### Games

`engine.js` exports `GameBase`: round loop with pause handling, `samplePos()` (envelope-bounded AND clamped on-screen via margins, staying body-anchored), `hit()`/`miss()` accounting, particle bursts, the always-drawn arm skeleton + hand cursor with capture-radius ring, and the "therapist voice" (`say()`, `_feedbackTick()` — spoken praise/tips, rate-limited).


**Catch Together** (`rgs`, **disabled since Sep 2026**: every game is for the one arm chosen at setup and this one is bimanual by definition — re-enable by deleting the flag) is a rebuild of the Rehabilitation Gaming System's own task (`Unity-simple-RGS-game`, and the spheroids paper `06091665.pdf`): balls approach in depth and are caught with **both hands cupped together** — a single hand cannot catch, and that coupling is the therapy — then carried to a colour-matched trough. Three graded stages (catch → carry → sort) stand in for RGS's four conditions, with the original's **wait-vs-continuous** pacing as a per-stage flag (one ball at a time is the difference between a task and a queue for a slow reacher). Lanes and troughs sit inside the measured envelope, which the original's fixed world positions did not. RGS's **observation condition** (the game plays itself while the patient watches) is deliberately **not** included: it is well-founded but it is a different intervention with its own consent conversation, not a difficulty stage, and a rehab game that takes the controls away mid-session reads as a freeze. `bothArms` must be true for it (set in `main.js#startGame`), and stage progression mirrors Drift's.

**Cloud Slingshot** (`sling`) is the Angry Birds mechanic rebuilt for the arm: reach the pouch, close the hand, pull back, hold the stretch, open to fire at towers of dark clouds. The pull *is* the exercise — a graded, held, eccentric reach ending in a release. **Power is normalised to the patient's own reach** (`_maxPull` = `rangeScale × envAt` in the pull direction), not to screen pixels as the reference does — with a fixed factor the game would be literally unwinnable for the people it is for. Simulated: the tower is reachable from ~40% of their reach, and a weaker shot still flies and lands visibly short rather than doing nothing. Release is hand-open, with **holding the stretch still for `SL_HOLD_MS`** as the no-grasp path — and that hold is worth asking for in its own right. `meanPullFrac`/`bestPullFrac` are logged: how deep into their own range each pull went is the number this game exists to move. Physics is ~200 lines written here; the reference carries Phaser + p2 (about 3 MB) to do the same job.

**Connect the Dots** (`dots`) is the point-to-point game: hold on dot 1, then 2, then 3, and a line follows until a picture closes. Levels add dots (10 → 44) and shrink the capture radius together — the same drawing asked for more precisely, like the paper puzzles that go 1-10 / 1-30 / 1-150. `dotsFromOutline` puts **every outline vertex on a dot first** and spends the spare dots on the longest edges: even arc-length spacing walks straight past corners, and a star resampled to 8 even points stops looking like a star. Dots are laid in the patient's own envelope and each one is pulled radially in to `spread × envAt(th)` if the picture's box would push it past their reach (the corners of any box sit further out than its axes), so a picture is never partly unreachable. Only the NEXT dot is lit and numbered — lighting them all is what makes a paper puzzle confusing; here there is always exactly one thing to go to. Squeeze is a shortcut over the dwell, never a requirement. Level banked via `store.getLevel/setLevel("dotsLevel")`.
**Memory Pairs** (`pairs`, Sep 2026, by request, from `mockups/memory-game-master.zip`) is the card-matching Memory game rebuilt for the arm: a grid of face-down cards, hold the hand on one to turn it (sticky dwell, never a click or a squeeze, so every turn is a reach and nothing is asked of the hand), a matching pair stays up, a mismatch turns back after `PAIR_SHOW_MS`. The grid is laid inside the measured envelope the way Connect the Dots lays its dots (a box on the axes the arm has, each card pulled radially in to `spread × envAt`, kept on screen), **then frozen in screen pixels for the whole board** (positions, `cardW/cardH`, `radiusPx`; hit-testing at `palmPx`) so a tracking re-snap never shifts a board the patient is trying to remember (Sep 2026, by request after the first play), and `PAIR_LEVELS` is the ladder (2×2 → 5×4, capture radius shrinking, spread widening; banked per patient as `pairsLevel`, up a level on every cleared board). Every board opens with a **peek** (all cards face up for `PAIR_PEEK_BASE + PAIR_PEEK_MS × pairs`, a thin bar showing the time left), so it is study-then-recall rather than guessing. A mismatch is counted as `wrongTurns` in the round record and **never** fed to `miss()`: the DDA reads motor performance and a forgotten card is not a motor error. The faces are drawn glyphs (`drawGlyph`: star, moon, heart, boat, fish, house, sun, cloud, lantern, anchor), not the mockup's emoji, because a clinic PC may render none. Per round: `pairsFound`, `turns`, `wrongTurns`, `boardsCleared`, `cards`.

**Scratch Cards** (`lens`, still `LighthouseLens` in the source) is the coverage game: the open hand scrapes foil flakes off a hidden picture. Its **level is the difficulty ladder, not the DDA** — `SCRATCH_LEVELS` widens the card across more of the patient's own measured envelope (`reach` × `envAt`) *and* shrinks the scratcher (`eraser`, 0.30 → 0.11 SW) together, so demand moves from big sweeps close in to accurate sweeps at full stretch. Every flake sits inside the measured envelope and on screen, so "clear the card" is never quietly impossible. One picture per level (`SCRATCH_CARDS`, procedural, drawn into the card's own box so it fits whatever shape that reach turns out to be), level banked per patient via `store.getLevel/setLevel("scratchLevel")` and resumed. It borrows only **anticipation and reveal** from commercial scratch cards; the rest of that playbook — variable-ratio rewards, near-miss teasing, prize framing — exists to keep somebody playing past the point they meant to stop, which in a clinical tool for older stroke patients is a harm, not a mechanic. The reward is the picture, it is certain, and it arrives when the work is done.

Pong's round-1 **tutorial** (skippable, replaces the story; rebuilt Sep 2026 by request for someone with cognitive as well as motor impairment: one thing at a time, shown before it is asked, a bare screen with only the court, the paddles, the ball, the landing spot and one line) has one step, `meet` (a slow ball from the star, `TUT_CROSS_MIN` 4.5 s across, aimed alternately at the upper and lower lane, with a dashed line to the pulsing spot where it will land on the patient's rail; three returns, a miss just brings it again, five tries at most), then `play`. It says nothing about trick shots (by request). Nothing scores in it. The meet step **doubles as the speed assessment**: paddle travel to the landing spot from the serve (`arrivedT`, so waiting there for the slow ball is not slowness) → median lane speed → traversal `T` → `pongCrossTime = 1.4×T + 0.45` clamped, persisted into `params.lifetime` by `main.js#onRoundEnd` (`paddleTraversalS` logged per round). **A game is 90 seconds** (Oct 2026, by request; Sep 2026 was best of five to `PONG_WIN` 3 with a trick clock per point, both gone): points are tallied both ways for `TRICK_AT` (90) seconds of play on **one game clock** (`_gameT0`, set by `_gameStart` when play begins after the tutorial; `gameT(now)`), then the patient's paddle is ablaze and their **next return is the smash**, which wins that point and **ends the game** (`_pointTo` → `_gameOver(now, trick)`; `roundSeconds` is a backstop of `TRICK_AT + TRICK_GRACE + ceremony`, and the clock ending the game still gives a board and a result, `update()` calls `_gameOver` 7 s before it). The game is **won, lost or drawn on the tally** (`matchWon` true / false / null), never on a target; the scoreboard is a running count (sun + number, grey disc + number, the style under each). The loader at the top of the court is the **game clock**: a **paddle catching fire** (`_drawRacket`: fills from the handle up over the game with flame tongues on the fire line, ablaze with flames above the head and sparks once full, the seconds left in its head and "smash in N s" beside it; calm motion keeps the fill and drops the flicker). Modes without a smash (bimanual, companion) get `_drawGameClock`, a shrinking line with the seconds. The game's one trick is the smash (`nextTrick = TRICKS[0]` in `setup`; the other four stay whole, a swap away): `_engageTrick` fires it and sets up the star's misread to match, so it lands by construction. The five: **smash** (straight, 1.8× faster, the star holds the side the ball came from), **curve** (sets off at the star, then bends away on a parabola into the far corner, `b.curve`), **ghost** (fades to a shimmer across the middle of the court, `GHOST_FADE`/`_ghostAlpha`, and the star, having lost it, stands still), **zigzag** (rail to rail all the way, `ZIGZAG_VY`, the star follows the last bounce the wrong way) and **feather** (floats at `FEATHER_FLOAT` to mid court drifting towards the star, then darts at `FEATHER_DART` into the corner, `b.dartX`). The ball's motion, trick included, lives in one place, `_stepBall`, and `_simToAI` runs it ahead so the star's arrival prediction is the ball's own physics (`_predictY` remains for the tutorial's landing mark); trick balls set `b.free` so `_capVy` leaves them alone. Each draws as itself (`_drawTrickBall`) with a long **trail** in its colours (`_drawTrail`, `TRICK_TRAIL_MS`; embers only on the smash; the ghost's tail fades with it; the feather's stays short until it darts), each has its own voice (`audio.trick(key)`), and only the smash shakes the court (`SHAKE_MS`, not under calm motion). None asks anything of the hand: the trick is earned by keeping the rally alive and fired by the same return as any other. A point can still be won or lost the ordinary way before that. **Every point ends with a ceremony** (`_pointTo` → `pointBreak` for `POINT_BREAK_MS`, drawn by `_drawPointBreak`): the point is announced out loud with the scoreline, patient's score first (`_announce` resets the therapist-voice throttle so it is never swallowed), POINT! or the trick's word (SMASH!, CURVE!, GHOST!, ZIGZAG!, FEATHER!) pops under a turning sunburst with confetti bursts for the patient's point, the star's point is a soft lavender card that dims the court a little and says the next serve is coming, and match point is named either way; then `_startServe` runs and the clock starts again. `_drawGameOver` holds the final board (GAME! or SMASH! GAME!, the tally, one sentence, then the style, the longest rally and the titles) for 6.5 s. The star's fatigue (`AI_FADE_*`) runs on the game clock. The **underdog** (trailing by `UNDERDOG_GAP` 3) gets a paddle `UNDERDOG_GROW` 15% taller until the gap is `UNDERDOG_CLOSE` 2 (`_updateUnderdog`, `_padH(edge)`, used by `_edgeHit` and `_padRect`; the centre never moves, so the arm-to-paddle mapping is untouched). **Orbs** (`_orbs`, on unless the staff dial `state.pongPowerups` is off): one at a time mid court every 7–12 s, collected by the *person* who last hit the ball (`lastHit`) sending the ball through it, for one of `POWERS`: big paddle (×1.5 for 8 s), shrink the opponent (×0.65 for 8 s), a shield (one save behind the goal, `shieldAt`), or a ghost shot (the next return fades across the middle via `b.ghost`/`_ghostAlpha`, and the star, having nothing to read, holds its line). Player two's paddle and label are teal (`PAD_COLS.mate`). Player two is a **partner**, not a patient: picked or named in the setup, their arm given a **quick measure** there (`renderPartnerMeasure`: three raises of the playing arm, about twenty seconds, `tracker.armAngle2` min/max → `store.savePartner(patient, name, {side: {arcMinDeg, arcMaxDeg}})`, kept under the patient; a patient already in the system can be picked too, on their own assessed profile; unmeasured, a 30–150° lane) and `duoProfile()` feeds it in as `p2Profile`. The **head-to-head** record and best rally ever per partner (`store.getRivalry/logRivalry/resetRivalry`, logged in `onRoundEnd`) shows in the setup with a two-step in-page reset, and under the between-rounds card (`#rc-board`). The between card for Pong is three lines: the tally and result, the longest rally with the style (both players' in duo) and orbs, the titles and the challenge. Duo rounds move the ball's pace like any game but leave the star's rank alone. The ball-speed and power-up dials live in the duo setup and the staff drawer (`in-pong-speed`, `in-pong-power`). **The star has a rank** (`STAR_RANKS`, exported from `games.js`; stored per patient as `starRank` via `store.getLevel/setLevel`, up a rank on a win, down on a loss): Little star → Bright star → Comet → Nova → Supernova, each a slightly brighter grey with more glow, a sparkle tail from Comet up, its name at its rail, and sharper reactions (`gain`/`vmax` replace the old fixed 3 / 0.24; the slip's `vmaxS` scales with it so the smash still lands short by construction). Rank 1 is the old star exactly. Serves launch from the **middle of the court travelling towards the opponent**, so a point opens with the patient's ball on its way out rather than one arriving at them. Long rallies resolve via the **misread**, not the old sleepy star (which drifted to lane middle and read as being handed the point): from `AI_SLIP_FROM` (80 s, backstop `AI_SLIP_BY` 85 s) the next ball heading to the AI is steered to the corner *away* from it (`_engageSlip`), the star holds the side the ball came from — anticipating a return to where it just was, the error people actually make — then breaks late and lunges. The release is on **time, not a fixed fraction of the flight** (`AI_SLIP_LATE`): it goes when there is just barely enough left to get back, and targets a spot `AI_SLIP_GAP` of a paddle past the ball (`_predictY` folds the rails in), so it arrives a sliver short by construction rather than by luck — simulated over 480 configurations, 0 accidental saves and a median miss of 0.29 paddle heights. `_slipUsed` allows it once per round, and a slip that did not pay off is dropped at the serve rather than banked. `_tired` survives as capped flavour (`AI_FADE_MAX`) and the "z z" is suppressed during a slip — a sleepy cue over a lunge would say the point was given rather than won. **Note:** `AI_SLIP_FROM`/`AI_SLIP_BY` are legacy constants; the slip is now engaged by the trick shot and nothing else. ### Audio

`audio.js` is all WebAudio. `startBgm(gameId)` tries `assets/music/<gameId>.mp3` first, falls back to a generative lo-fi engine (per-game moods). Melody Tiles instead uses `startSong(chart)`: the engine plays drums/bass/chords on a beat clock (`songBeat()`), and the *game* plays each melody note on tile hit (`playMelodyNote`) — a miss is an audible gap, so misses are silent (`miss(target, true)`). Song charts live in `songs.js` (beats, midi pitch, duration; C-major-ish, difficulty 1–3).

### UI conventions

- Menus are **mouse + keyboard** driven (hand-cursor dwell/squeeze selection was removed by request): arrow keys move a `.kbd-focus` highlight through the `data-dwell="1"` elements of the current menu screen, Enter/Space selects (keydown handler at the bottom of `main.js`). `data-dwell` now just marks keyboard-navigable elements.
- **The opening stretch** (Oct 2026, by request; `js/warmup.js`, `Warmup`): a brief warm-up that **opens the day's assessment** (`startAssessment` runs `startWarmup(then)` first, once a session via `state.warmedUp`, reset whenever the welcome screen shows; the ✕ skips the stretch and goes straight into the measurement via `state.warmupThen`; a staff re-measure with `override` skips it) and is also offered on the welcome screen as *Warm up first* beside Start, led by the **Stretch Break video** (`WARMUP_SRC`, `assets/music/Stretch_Break.mp4`, about two minutes: five seated moves, overhead, cross-body both sides, wrist and prayer, with its own titles, countdowns, captions and voice; **the right file since Oct 2026, by request**). The video is large on the left in its own 16:9 shape and the patient sits beside it, cropped to the person with their skeleton (`_drawPersonPanel` in `warmup.js`, the camera picture covering the panel and slid so the tracked body is in the middle); `WARMUP_STEPS` marks where each move begins, for a note and a little shower of light (and the move's name spoken only if the browser refuses sound and the video plays muted); a cheer ends it; the ✕ ends it at any time. Nothing is measured or stored but the play time (`store.logPlaytime(…, "warmup")`); then the hub.
- The welcome screen is a setup gate (`watchWelcome` in `main.js`): it draws a live skeleton mirror on `#welcome-canvas` (amber → sage when framed), shows a tracking/feature status line, guides the patient to sit centered at the right distance (`framingMessage`), and starts on lift+squeeze (fast), lift-hold (fallback), the Start button, or a click. Only the **trained** hand is watched: the arm is chosen at login and the welcome lift never changes it.
- In-game UI is diegetic/no-HUD: no numbers except where the count IS the test (Harbor Crates). Feedback is glow, music, and spoken lines.
- Calm night-harbor visual language; palette anchors: cream `#f4ecdd`, amber `#e8a86a`, sage `#9fc08a`, ink `#1b1b3a` (see DESIGN_BRIEF.md).
- Patient-facing text is gentle and non-judgmental (misses are "soft"); it's aimed at an older stroke population.
- **Gentle-pacing theme (applies to every page and interaction)**: users are older, with small, slow movements. Timings generous (long timeouts, no rush), capture radii forgiving, motion thresholds tremor-tolerant, speech unhurried (rate 0.9), text large, one thing asked at a time, flows linear with no dead ends. When tuning any threshold or delay, err on the slow/forgiving side.
- **Flow rules** (from older-adult UX literature: default-first, progressive disclosure, ask-once): every menu screen pre-focuses one recommended action (`.kbd-focus` + "Start here" chip on select; current mode on Pong tiles; "Play again" between rounds) so a single Enter continues the session; the arm is chosen **once, at login** (the `login-arm` step, asked only when the record has no `arm`; stored by `store.setArm`, read by `loginAs` into `state.side`; the staff drawer's arm select is the therapist's override and writes the same field) and never re-asked — the assessment and every game are for that arm alone; screens fade in (`screenfade`); the welcome and select screens speak their guidance (throttled `speak()` in `main.js`).

### Accessibility (a11y.js)

`a11y.js` holds the live `A11Y` state (mirrored from the patient's saved settings on login and on every drawer change), `applySettings`, and `speakLine` — the single speech path (rate, patient-set voice volume, optional on-screen caption in `#caption`). All app speech goes through it (`main.js speak`, `GameBase._speak`, `coach.js`); in-game `say()` and stories skip the caption because `#cue`/`#prompt` already show the text. Per-patient settings live in `store.getSettings/saveSettings` (captions, dwell time, capture-radius scale, squeeze ease → `tracker.setSqueezeEase`, high contrast, calm motion, text scale, practice mode, visual-field flag, per-bus volumes) and are edited in the staff drawer's Comfort section. Engine-level behaviors: `samplePos` respects the visual-field policy (comfort = bias spawns to the intact side; scan = train the cut side — hemianopia is independent of the reach envelope), `glow()` adds dark rims in high-contrast mode, `burst()` softens under calm motion, `miss()` is a no-op in practice mode (and `main.js#onRoundEnd` skips logging/DDA), the welcome skeleton goes dashed when not framed (amber/sage is a red-green confusion pair — never signal by that hue pair alone), and every 4th round (or a compensation spike) triggers a spoken rest suggestion. `audio.js` has `musicBus`/`fxBus` gains (`setVolumes`).

### Persistence

`storage.js`: single localStorage key `rehabsuite-v1`, per-patient records (per-arm profiles + assessment history, session rounds capped at 400, stars/unlocks, fatigue answers, `shoulderCm` = therapist tape-measured shoulder width entered once in the staff drawer — everything internal stays in SW units; `SW × shoulderCm` converts to real cm for the profile screen and export). Round records are appended by `main.js#onRoundEnd`; the therapist profile screen and JSON export read from here. Bump/migrate carefully — clinician data lives only in the browser.
