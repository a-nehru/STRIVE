# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

STRIVE (formerly Star Harbor / "Rehab Suite") — a webcam-based upper-limb rehabilitation game suite for stroke patients, developed by Synapse Lab, Shirley Ryan AbilityLab. UI copy convention: no em dashes in patient-facing text. Plain static site: vanilla JS ES modules, no build step, no dependencies to install, no tests or linter. MediaPipe Pose is loaded from CDN at runtime (internet required on first load). Design decisions are grounded in two rehab papers (CFI framework, Rehabilitation Gaming System) — README.md has a table mapping paper concepts to code; SPEC.md and DESIGN_BRIEF.md hold the full spec and visual design language.

## Run

```
python -m http.server 8321
```

then open `http://localhost:8321` (or double-click `start_game.bat`). A server is required — camera access is blocked on `file://` pages. Testing requires a webcam and allowing camera access; data persists in the browser's localStorage under the key `rehabsuite-v1` (do not rename the key — it would orphan patient data).

**ZED 2 (optional):** `python tools/zed_bridge.py` runs the ZED SDK's depth-based body tracking (BODY_38) and streams it on `localhost:8322` (`/status`, `/stream` SSE skeletons in MediaPipe 33-landmark layout, `/video.mjpg` mirror preview). Each skeleton carries `lm` (normalized 2D) **and `lm3` (the same joints in metres, camera frame: x right, y down, z forward)** — the depth channel `tracker._ingest3`/`hand3(side)`/`has3D` expose and the assessment turns into a real workspace volume; a webcam has no depth, so the volume is simply absent there rather than estimated. With the staff-drawer "Camera source" setting on Auto (the default, stored device-level in localStorage `strive-cam-source`), `tracker.js` probes the bridge at boot and uses the ZED when it's up, webcam + MediaPipe otherwise; the source is chosen once at boot, so changing the setting reloads. In ZED mode the 21-point hand model is unavailable — grasp runs on the self-calibrating pose-fingertip fallback (BODY_38's fingertip points), and hand-model games (Firefly Pinch etc.) degrade. Requires ZED SDK + pyzed on the machine; the game itself never needs it.

**Two players (ZED only):** `python tools/zed_bridge.py --bodies 2` streams two seats. Seats are assigned by **where people stand** (seat 0 = left-most in the image at lock time), then followed by ZED tracking id — never by confidence, which is what would hand a paddle to the other player mid-rally. A seat is held through `--seat-grace` seconds of occlusion, then re-seats to the nearest unclaimed body; `GET /relock` forces a re-seat. Who is a candidate at all is decided **first by where they stand**: `in_play()` admits only bodies inside the play volume (`--play-near`/`--play-far` metres deep, `--play-width` metres wide about the camera axis; defaults 0.6-2.5 m x 2.6 m), so a therapist standing behind the patient is never in the running whatever the detector scores. Tracking ids do not survive somebody leaving the room, so each seat also remembers a **build signature** — biacromial width, torso length and height in metres from depth, EMA-smoothed, matched within `--sig-tol` when a free seat is refilled (`build_signature`/`sig_distance`). That is deliberately **not** face recognition: no extra model, no biometric stored, and enough to tell apart the two or three people actually in a therapy room. The payload keeps seat 0 as the top-level `lm`/`lm3`/`shm` (the single-player game reads it unchanged) and adds `bodies: [{seat, id, lm, lm3, shm}]`. `tracker.js` routes seat 1 into `_ingestSecond` — a deliberately thin second body (shoulders, wrists, trunk only) exposing `armAngle2(side)`/`p2TrackingOk`, touching none of `pts`/`anchor`/`frame`, so compensation, grasp, relocation and the DDA can never be moved by a second person in the room. Pong's `duo` mode uses it: each player's arm side is chosen once in `renderDuoSetup` (`main.js`) and fixed for the round, player 2 is a saved patient whose own `arcMinDeg/arcMaxDeg` drives their paddle (guest = default arc), an untracked player 2's paddle **holds position** rather than snapping to center (a snap would gift a point), the round-1 tutorial is skipped (it is a solo speed measurement), and `score.ai` doubles as player 2's tally. The mode needs the ZED: one webcam pose model reports a single body, so the tile explains itself instead of failing mid-round.

Two ZED tools sit beside the bridge, both reusing its `PROFILES` and `resolve_indexes()`, plus `tools/zed_common.py` (the shared `Readout` that turns one BODY_38 skeleton into the overlay and the numbers — so the two tools can never report different values for the same pose; it imports opencv lazily so the diagnostic can still run and *report* a missing opencv), so they test the path the game actually uses (stop the bridge first — one process at a time can hold the camera): `python tools/zed_test.py` is the staged diagnostic (pyzed import, CUDA GPU via `nvidia-smi`, device enumerated, open, measured fps, depth validity, BODY_38 detection rate, biacromial width, and whether the landmarks the game needs actually fill in), exit 0 when every stage passes, and during the body stage it shows the RGB feed with the skeleton and the live tracking numbers (`--no-preview` for headless); `python tools/zed_view.py` is the live window (skeleton, per-joint XYZ in the SDK camera frame, the same points in SW units with a 1-SW ring, 3D elbow flexion, `armAngle` elevation, and the grasp state replayed with `tracker.js`'s own `GRIP_*` constants so it agrees with the game). Run them from Windows Python, not WSL — WSL cannot see the camera without USB forwarding. The ZED needs no manual calibration (factory-calibrated, SDK self-calibrates at open); the calibration that matters is the in-game assessment, plus letting the fingertip grip envelope widen by opening and squeezing a few times.

**Therapist contact (optional):** `python tools/mail_bridge.py` runs a local SMTP relay on `localhost:8323` (`GET /status`, `POST /send {kind, subject, body}`). A static page cannot send email, and the alternatives both fail this project — a third-party email API would need its key embedded in a public page and would route patient data through somebody else's server, while `mailto:` alone only opens a client and waits for a human. So mail goes the way body tracking does: through a local service, with the credential in gitignored `tools/mail_config.json` (copy `mail_config.example.json`; Gmail needs an **app password**) or `STRIVE_SMTP_*` env vars, read only by that process and never by the browser. `python tools/mail_bridge.py --test` sends one message and exits, to check setup without opening the game. `js/mail.js` probes it at boot and the staff drawer's **Therapist contact** section gets three buttons — *Send test email* (connectivity + diagnostics), *Report a problem* (a typed description plus `diagnostics()`: camera source, tracking state, people seen, hand model, arm lengths, browser), *Email progress* (`progressReport()`: the arm's assessment, workspace area/volume/coverage/quadrants, edges reached, grasp, the last 10 rounds, compensation). With the relay down every button falls back to a prefilled `mailto:` so nothing dead-ends. **Nothing sends automatically** — not on login, not on round end: patient data leaving the machine is always a deliberate press, which is a consent question and not a feature to optimise away.

## Deploy

Live site: **https://a-nehru.github.io/STRIVE/** — GitHub Pages, deployed automatically from `main` of https://github.com/a-nehru/STRIVE (legacy branch build, repo root). To publish: commit, push, wait ~1–2 min. **Always bump the `?v=N` query on the `style.css` and `main.js` references in `index.html` in the same commit** — Pages caches assets for 10 min and browsers hold them longer; the version bump is what makes deploys show up immediately. Verify a deploy by curling the live file for a string unique to the new commit, not just HTTP 200.

## Architecture

Data flow: webcam → MediaPipe Pose (`tracker.js`) → body-relative coordinates → assessment (`assessment.js`) → per-arm profile → games (`games.js` on `engine.js`) → round stats → DDA (`dda.js`) → updated params → localStorage (`storage.js`). `main.js` is the app shell that wires screens, rounds, and the staff/therapist UI together.

### The coordinate system (everything depends on this)

All game/assessment positions are in **shoulder-width units (SW) relative to the shoulder midpoint, y-up** — camera-distance independent and comparable across sessions. `tracker.js` owns the conversions: `handRel(side)` (hand in SW), `relToPx`/`pxToRel` (SW ↔ canvas pixels), `pxPerSW(canvas)`, `armAngle(side)` (arm elevation in degrees vs the trunk axis, 0 = down, 180 = overhead), plus `palm(side)` and `handClosed(side)` (grasp detection — used by Harbor Crates grab/release, Pong skill shots, the assessment squeeze, and the palm disc on the skeleton). Grasp runs two-tier: a dedicated **Hand Landmarker** (21 pts/hand, every 2nd frame, matched to pose wrists by proximity) gives finger-curl via `handCurl(side)`, with **self-calibrating per-person thresholds** (`curlCal` envelope: once enough curl range is seen, "closed" = 35% into that patient's own range, so a partial squeeze still registers; fixed 1.25/1.55 hysteresis until then); if it has no fresh detection, a self-calibrating pose-fingertip heuristic (`grip(side)`) is the fallback. Video coordinates are mirrored (`x = 1 - lm.x`) so the game acts like a mirror. A **stereo webcam** (a ZED plugged in as plain UVC, with no bridge running) delivers one double-wide `left eye | right eye` frame; `tracker.isStereo` (aspect ≥ `STEREO_RATIO` 2.6) detects it and everything reads `srcW`/`srcH` instead of `videoWidth/Height` — `_detectSource()` feeds both models a left-eye crop and `drawVideoMirror` blits only that half, so the patient never sees the room twice and MediaPipe never searches a squashed 2:1 image.

Envelope-based targets and the assessment circle are centered on `CENTER` (exported from `engine.js`) — **adaptive per patient**: the assessment captures the resting hand position at settle as the work center — the rest position IS zero (only a wild-tracking sanity clamp at ±1.4) — stores it as `profile.center`, and `GameBase.start()` loads it (default `{0, 0.25}` for older profiles), so limited-motion patients never travel to a preset spot and games place targets around the same point the envelope was measured from. The sweep screen is deliberately sparse — it used to carry a dashed arm-length circle, a square framing it, sixteen large direction dots, a seven-blob pacer running most of the sweep, a heavy glowing envelope and three separate marks on the hand, which is a lot of scenery over a measurement. What is left: a start-point dot, small direction dots that hug the patient's own traced shape (the only "what have I not covered" signal), the painted envelope drawn thin, a short pacer firefly that fades once they are clearly going round on their own, and the red hand cursor. **No preset guide circle** — the arm-length boundary is implied by the pacer and the hold targets rather than drawn three times. `CENTER` is mutated in place; `samplePos`/`fromCenter` read it live.

**Shoulder width is the ruler, arm length is the reach.** SW normalizes camera distance, but the AL/SW ratio varies ~1.2-1.7 between people and SW is a *projected* width that shrinks a few percent when the trunk turns — so "0.9 SW" is a different fraction of reach for different patients and different postures. `tracker.armLenSW(side)` keeps arm length (shoulder→elbow→wrist summed, bend-invariant) as a **decaying session max**; the assessment stores it as `profile.armLenSW` and `GameBase.start()` sets `armScale = clamp(live/stored, 0.8..1.25)`, which `envAt()` applies — so `rangeScale` means the same fraction of *this* reach every session. Sitting closer or further also has to move the frame's **scale**: the origin stays locked (a reach must never drag the world) but `_ingest` re-snaps `frame.sw` after `SCALE_HOLD` ms of >`SCALE_DRIFT` change **confirmed by the torso length moving the same way** — biacromial width alone shrinks on yaw, torso length barely does, so a turn can't be mistaken for a distance change.

**Who the tracker follows.** MediaPipe runs at `numPoses: 3` on purpose: asking for one body means the model silently hands over whoever it scored highest *this frame*, so a therapist or a second patient can become "the" body mid-round. `_pickBody`/`_feature` keep our own lock instead — cost = per-frame midpoint displacement + shoulder-width mismatch + build-ratio (torso/SW) mismatch, gated at `LOCK_GATE`; no acceptable match means **pause, never swap**, and only after `LOCK_GRACE` ms is a new (most central) person accepted. `relock()` forgets it — `loginAs` calls it. `tracker.peopleSeen` is the count, for staff diagnostics. This is a build signature, not a face: face recognition would mean an embedding model and storing patient biometrics for no gain in a room with two or three people. The ZED path does the same job in the bridge (play volume + build signature, above).

Rendering and hit-testing go through the tracker's **stable frame** (`tracker.frame`): a snapshot of the body anchor that stays fully locked for the whole round (so reaches/sway/jitter never move the world) and re-snaps only at `setBaseline()` (round start, after a relocation pause). The live anchors are for compensation/relocation signals only.

The tracker keeps the body anchor on two time scales: a slow filter (targets follow legitimate repositioning) and a fast filter. Fast-vs-slow divergence is the **compensation signal** consumed by `coach.js` (trunk lean / shoulder hike / rotation → amber skeleton, world dim, spoken cue, logged event). Large sustained change triggers `relocated()` → graceful pause + re-baseline in the game loop.

### Assessment → profile → difficulty

`assessment.js` (one screen, **both arms back to back — left then right, nothing to choose**: hold still → **squeeze calibration** ("open wide… now squeeze": captures the hand's own curl range → `tracker.setCurlCal` + `profile.curlCal`, loaded by `GameBase.start`; skipped gracefully without hand-model detection) → **demo** → 3-2-1 countdown → **sweep** → **6 held positions**). `main.js#startAssessment` runs `ASSESS_ORDER` via `runAssessmentArm`; the arm being measured is tagged in every prompt (`opts.label`). **A stored ROM is reused, never redone** — an arm that already has a profile is skipped, and only an explicit re-measure replaces it. `startAssessment({force, arms})` takes **which arms**: the staff drawer has *Measure both arms* and *Re-measure this arm*, the profile screen's button redoes the arm it is showing, and the select card redoes both. Redoing one arm is the common case — range changes on the affected side while the other stays put, and making a therapist sit a patient through six minutes to refresh three numbers is how a re-measure stops happening at all. The replaced profile goes to `history[arm]`, and `store.saveProfile` now keeps it **whole enough to compare against** (area, coverage, volume, quadrants, extremes, grasp — an arc and an envelope alone cannot answer "is their workspace bigger than last time"). Finishing an assessment lands on **`#screen-romcompare`** (`renderRomCompare`), not back on the menu: per arm, the previous envelope dashed under the current one at a shared scale, then arc / area / coverage / volume / longest reach / edges reached / grasped-there as `was → now` with a signed delta. With no previous measurement each row reads *baseline*, never a blank. A re-measure that never shows the difference is just a delay. The **demo** step (`_drawDemo`, `DEMO_MS`) shows a figure sweeping the full circle before the patient is asked for it — words alone make an older patient translate "the biggest circle you can" into a movement, and nothing is measured while they watch opens with a **hand-choice step** (two lights over the mirror; the hand held on its light — squeeze or 1.2 s hold — is the one assessed, and `main.js#startAssessment` adopts `profile.arm` as the session side) over a **live mirrored camera feed + skeleton** backdrop (`drawVideoMirror`/`drawBody`, exported from `engine.js` and shared with the welcome screen and Harbor Crates). Each run produces a per-arm profile: `envelope[16]` (max radial reach per 16 angular bins, SW; unreached bins floored at 0.45 with `covered` recording the measured fraction), `arcMinDeg`/`arcMaxDeg` (+`arcMeasured`), `jitter`, `loopSeconds` (from total swept angle, wrap-safe), `grasp[]` (each orb: `ok` = hold succeeded, `stability` = final successful hold only, `squeeze` = real hand-close observed — hold is the pass/fail so patients without grasp still complete). The **sweep** is **90 s of free reach** (`SWEEP_MS`), and the patient is told plainly why — *wherever you reach is where your targets will appear*. It ends early only when there is genuinely nothing left to find (`SWEEP_DONE_BINS` = 14 of 16 covered — not 16, because the bins straight below `CENTER` sit inside `REC_R` of the resting hand and can never register — **and** no new ground for `SWEEP_STALL_MS`), so nobody is rushed off the measurement everything else is scaled from, nor made to flail at a finished one; tracking-loss pauses freeze every assessment timer. The sweep carries no edge checkpoints — chasing one mid-circle distorts the shape — because the **held positions** step measures the edges properly straight afterwards: six directed reaches (`out`, `up-out`, `overhead`, `up-across`, `across`, `down-out`, mirrored per arm by `_extTheta` so both arms are asked for the same *movements*, not the same screen spots) to `EXT_REACH` of the true arm-length boundary (`_demoR`), scored on the **projection** onto the direction so drifting off-axis can't look like a longer reach. Each is **held 5 s** (`HOLD_MS`, sticky through a 400 ms tremor exit) **with an open-and-close of the hand** cued partway in, recording `{reached, frac, reachSW, holdMs, stability, squeeze, release, graspOk}`. Reaching is the pass/fail and grasping never is, so a patient with no hand function still completes every position. This replaces the separate 3-orb grasp phase entirely: `profile.grasp` is now a *view* of these positions (one source of truth, and the therapist's map keeps working), plus `reachablePositions`/`graspPositions` — **where** a patient can grasp, not just whether, is what game allocation needs. The sweep records where the patient *went*; only this records whether they *can* get to the edge and work there. Nobody is cut off mid-reach — the clock only bites once the reach stops growing — and a short reach is a measurement, never a failure on screen. **Workspace readouts** (all from `envRaw`, the *unfloored* envelope — `envelope` is floored at `ENV_FLOOR` so games have somewhere to put targets, and area must not inherit that): `areaSW2` (shoelace over the 16 bin triangles), `coverage` = area / π·armLen² (fraction of the arm's full reachable disc), `quadrants` {upOut, upAcross, downAcross, downOut} named for the assessed arm, and — **ZED only** — `volumeM3` as a per-sector prism sum (each wedge extruded by how far the hand travelled forward and back *in that sector*, `zLo`/`zHi` from `hand3`) plus `depthRangeM`. `shoulderM` is stored too, so the cm/cm² conversion is self-contained. All of it surfaces on the therapist profile screen and in the progress email. Games must not spawn targets outside `rangeScale × envelope` — that is a clinical constraint, not a style choice.

Difficulty is stored **per game and per arm** (`store.getGameParams`/`saveGameParams`/`listGameParams`, shown on the therapist profile screen): the games make different demands, so a patient doing well at Pong is not necessarily ready for a harder Scratch Card. A game never played falls back to `profile.params`, and `profile.params` is deliberately left at the **assessment-seeded** value — a first play starts from what the patient was measured at, not from wherever the last game drifted to. `main.js` keeps the round's actual params in `state.roundParams` and the DDA adjusts from those. Ladder levels (`scratchLevel`, `dotsLevel`, `pongLevel`) are stored separately via `store.getLevel/setLevel`. `dda.js` defines the three difficulty params (`rangeScale`, `radius`, `lifetime`) with hard `LIMITS`, seeds them from the assessment (`initialParams`), and adjusts between rounds: hit rate >70% harder, <50% easier; when easing, `missFar` (misses beyond 70% of range demand) decides whether to reduce range demand vs grow radius/lifetime. `main.js` additionally holds difficulty steady if ≥3 compensation events occurred in the round.

### Games

`engine.js` exports `GameBase`: round loop with pause handling, `samplePos()` (envelope-bounded AND clamped on-screen via margins, staying body-anchored), `hit()`/`miss()` accounting, particle bursts, the always-drawn arm skeleton + hand cursor with capture-radius ring, and the "therapist voice" (`say()`, `_feedbackTick()` — spoken praise/tips, rate-limited).


**Connect the Dots** (`dots`) is the point-to-point game: hold on dot 1, then 2, then 3, and a line follows until a picture closes. Levels add dots (10 → 44) and shrink the capture radius together — the same drawing asked for more precisely, like the paper puzzles that go 1-10 / 1-30 / 1-150. `dotsFromOutline` puts **every outline vertex on a dot first** and spends the spare dots on the longest edges: even arc-length spacing walks straight past corners, and a star resampled to 8 even points stops looking like a star. Dots are laid in the patient's own envelope and each one is pulled radially in to `spread × envAt(th)` if the picture's box would push it past their reach (the corners of any box sit further out than its axes), so a picture is never partly unreachable. Only the NEXT dot is lit and numbered — lighting them all is what makes a paper puzzle confusing; here there is always exactly one thing to go to. Squeeze is a shortcut over the dwell, never a requirement. Level banked via `store.getLevel/setLevel("dotsLevel")`.
A game subclass supplies: `id` (class field, must match its entry in the `GAMES` array at the bottom of `games.js` and its `CARD_ART` key in `main.js`), `setup()`, `update(now, dt)`, `drawBg(ctx, c, now)`, `draw(ctx, c, now)`, and optional `extra()` for per-game round metrics (these flow into the round record, the between-rounds summary text in `main.js`, and the therapist log). Interaction is dwell-based in most games ("grab" = hold hand on target); Harbor Crates uses real hand-close detection (`tracker.handClosed`) — a grasp *event* (arrive open, then squeeze) to grab, open past the midline to release, at the **palm** (`tracker.palmRel`, wrist fallback), not the wrist; it plays in **AR** (camera feed + skeleton via `drawVideoMirror`/`drawBody`) with a **bench** (`benchY`) the blocks spawn on, the delivered pile builds on (visible count), and a solid BBT **barrier partition** stands on: crossing the midline below the barrier top (`barrierY`, scales with `rangeScale`) pins the crate against the wall until the patient lifts it over. Round flow: **practice → 3-2-1 → 60 s test** — round 1 opens with an untimed, voice-guided practice transfer (squeeze → lift over → open), later rounds go straight to the countdown; during the test a big `m:ss` timer sits top-center with a soft per-second tick (brighter final 5 s), and the clock (`startT`) is frozen until the test phase starts. Hands render as real hands everywhere: `drawHand` in `engine.js` draws the 21-point hand skeleton (palm web + fingers, amber open / sage closed) over the patient's actual hand, with the glow-dot cursor as fallback — used by `drawBody`, the game engine's cursor, and the assessment. The cursor and ALL hit-testing sit at the **palm center** (`palmRel`/`palmPx`, wrist fallback), not the wrist — `GameBase.handNear/handNearFor/handDist` and the assessment's hand position are palm-first. **Only four things are enabled right now** (Aug 2026, by request): the assessment, **Arc Pong**, **Scratch Cards** and **Connect the Dots**. Every other entry in `GAMES` carries `disabled: true` — the code is all still there, so re-enabling one is deleting that flag. Twenty-four games exist in total: the nine originals plus fifteen from the Aug 2026 research pass (clinical rationale per game in GAME_IDEAS.md). A `disabled: true` flag on a `GAMES` entry hides its card and its drawer settings; entries also carry `trains` (the one movement trained, shown as a chip on the card — therapists prescribe by movement).

**Scratch Cards** (`lens`, still `LighthouseLens` in the source) is the coverage game: the open hand scrapes foil flakes off a hidden picture. Its **level is the difficulty ladder, not the DDA** — `SCRATCH_LEVELS` widens the card across more of the patient's own measured envelope (`reach` × `envAt`) *and* shrinks the scratcher (`eraser`, 0.30 → 0.11 SW) together, so demand moves from big sweeps close in to accurate sweeps at full stretch. Every flake sits inside the measured envelope and on screen, so "clear the card" is never quietly impossible. One picture per level (`SCRATCH_CARDS`, procedural, drawn into the card's own box so it fits whatever shape that reach turns out to be), level banked per patient via `store.getLevel/setLevel("scratchLevel")` and resumed. It borrows only **anticipation and reveal** from commercial scratch cards; the rest of that playbook — variable-ratio rewards, near-miss teasing, prize framing — exists to keep somebody playing past the point they meant to stop, which in a clinical tool for older stroke patients is a harm, not a mechanic. The reward is the picture, it is certain, and it arrives when the work is done.

Optional game fields: `tips.objective` is auto-spoken as a reminder after ~12 s without interaction; `GameBase.dwellProgress(key, inside, now)` is the sticky dwell (survives brief tremor exits — use it for new dwell interactions). Modes: `pong` has 6 modes chosen via an in-flow tile picker (`renderPongModes` in `main.js`, kept in sync with the drawer select) plus grip/spin skill shots (level-based unlock in `store.getPongLevel`, or staff override); `drift` has 3 stages that progress on hit rate in `main.js`; `oars` (together/bailing) and `ferry` (solo/wheel) pick modes via drawer selects. Tier-2 games (`teapot`, `glide`, `bloom`, `pinch`) need a fresh Hand Landmarker — they coach "bring your hand closer" instead of failing silently, via `tracker.palmFacing` / continuous `handCurl` / `pinchOnly`; `tracker.handVel` (SW/s) powers the swipe game. Pong draws **no arm**: the translated skeleton was a second moving shape competing with the ball, and the capture ring is meaningless in a paddle-driven game. What is left is a **small translucent hand sitting on the paddle it drives** (`_handPads`/`_drawArmAndCursor`, `PONG_HAND_SCALE/ALPHA/OUT`), still curling and closing live, nudged outward so it hugs the back of the paddle instead of spilling into the court — and each paddle gets the hand that actually drives it, so in bimanual the left paddle shows the left hand. `state.pongSkills` defaults to **`"auto"`** (level unlock: 1 rally → 2 +grip → 3 +spin). It used to default to `"both"`, which handed a brand-new patient the **Grip Shot** in round 1 — squeezing as the ball arrives *catches* it and pins it to the paddle until the hand opens (or 1.2 s), which without warning reads as the ball sticking to your hand. Pong plays in a **walled lane** (`wallTop`/`wallBottom`, sized by `rangeScale` + paddle height): the ball rebounds off visible rails at the edges of the paddle's reachable track so it can never go where the paddle can't, the assessed arc maps onto the lane, serves/AI aim inside it, and `_capVy` keeps |vy| ≤ 38% of |vx| so rallies stay flat instead of ricocheting. Ball speed is **constant within a rally** (every return resets to `baseVx`; the crossing time is `pongCrossTime || params.lifetime` — difficulty moves only between rounds). Pong's round-1 **tutorial** (skippable, replaces the story) doubles as a speed assessment: five top↔bottom star touches → median traversal → `pongCrossTime = 1.4×T + 0.45` clamped, persisted into `params.lifetime` by `main.js#onRoundEnd` (`paddleTraversalS` logged per round); tutorial misses give the AI no points. A game is to **`PONG_WIN` = 5 points** (`_checkMatch`): reaching five ends the round on a scoreline instead of on a clock, and losing is allowed to happen — an opponent that cannot win is not an opponent — but it is never framed as the patient's failure. Serves launch from the **middle of the court travelling towards the opponent**, so a point opens with the patient's ball on its way out rather than one arriving at them. Long rallies resolve via the **misread**, not the old sleepy star (which drifted to lane middle and read as being handed the point): from `AI_SLIP_FROM` (80 s, backstop `AI_SLIP_BY` 85 s) the next ball heading to the AI is steered to the corner *away* from it (`_engageSlip`), the star holds the side the ball came from — anticipating a return to where it just was, the error people actually make — then breaks late and lunges. The release is on **time, not a fixed fraction of the flight** (`AI_SLIP_LATE`): it goes when there is just barely enough left to get back, and targets a spot `AI_SLIP_GAP` of a paddle past the ball (`_predictY` folds the rails in), so it arrives a sliver short by construction rather than by luck — simulated over 480 configurations, 0 accidental saves and a median miss of 0.29 paddle heights. `_slipUsed` allows it once per round, and a slip that did not pay off is dropped at the serve rather than banked. `_tired` survives as capped flavour (`AI_FADE_MAX`) and the "z z" is suppressed during a slip — a sleepy cue over a lunge would say the point was given rather than won. **Note the interaction:** a 5-point game usually finishes well before 80 s, so the slip only fires in genuinely long matches; lower `AI_SLIP_FROM` if it should be the normal ending. Paddles hang from **rope rigs** (pulley + character helper: puzzle hero = patient, dark cloud = AI, friends = mates/companion — cast shapes shared with Rainbow Crossing). `rainbow` (Rainbow Crossing, Strivealon lore, flat ink-on-cream daylight look) trains shoulder **external rotation**: outward forearm sweep with an elbow-planted gate (`_updateSweep`) whooshes clouds; friends are saved by squeeze-or-hold; its round-1 tutorial is skippable and it overrides `_drawArmAndCursor` for the light background.

### Audio

`audio.js` is all WebAudio. `startBgm(gameId)` tries `assets/music/<gameId>.mp3` first, falls back to a generative lo-fi engine (per-game moods). Melody Tiles instead uses `startSong(chart)`: the engine plays drums/bass/chords on a beat clock (`songBeat()`), and the *game* plays each melody note on tile hit (`playMelodyNote`) — a miss is an audible gap, so misses are silent (`miss(target, true)`). Song charts live in `songs.js` (beats, midi pitch, duration; C-major-ish, difficulty 1–3).

### UI conventions

- Menus are **mouse + keyboard** driven (hand-cursor dwell/squeeze selection was removed by request): arrow keys move a `.kbd-focus` highlight through the `data-dwell="1"` elements of the current menu screen, Enter/Space selects (keydown handler at the bottom of `main.js`). `data-dwell` now just marks keyboard-navigable elements.
- The welcome screen is a setup gate (`watchWelcome` in `main.js`): it draws a live skeleton mirror on `#welcome-canvas` (amber → sage when framed), shows a tracking/feature status line, guides the patient to sit centered at the right distance (`framingMessage`), and starts on lift+squeeze (fast), lift-hold (fallback), the Start button, or a click. Both hands are watched: **the lifted hand chooses the session side** (`state.side`, synced to the drawer's arm select); the button/click paths keep the current side.
- In-game UI is diegetic/no-HUD: no numbers except where the count IS the test (Harbor Crates). Feedback is glow, music, and spoken lines.
- Calm night-harbor visual language; palette anchors: cream `#f4ecdd`, amber `#e8a86a`, sage `#9fc08a`, ink `#1b1b3a` (see DESIGN_BRIEF.md).
- Patient-facing text is gentle and non-judgmental (misses are "soft"); it's aimed at an older stroke population.
- **Gentle-pacing theme (applies to every page and interaction)**: users are older, with small, slow movements. Timings generous (long timeouts, no rush), capture radii forgiving, motion thresholds tremor-tolerant, speech unhurried (rate 0.9), text large, one thing asked at a time, flows linear with no dead ends. When tuning any threshold or delay, err on the slow/forgiving side.
- **Flow rules** (from older-adult UX literature: default-first, progressive disclosure, ask-once): every menu screen pre-focuses one recommended action (`.kbd-focus` + "Start here" chip on select; current mode on Pong tiles; "Play again" between rounds) so a single Enter continues the session; the hand is chosen **once** (`state.sideChosen` — welcome lift, drawer, or the assessment's chooser as fallback) and never re-asked; screens fade in (`screenfade`); the welcome and select screens speak their guidance (throttled `speak()` in `main.js`).

### Accessibility (a11y.js)

`a11y.js` holds the live `A11Y` state (mirrored from the patient's saved settings on login and on every drawer change), `applySettings`, and `speakLine` — the single speech path (rate, patient-set voice volume, optional on-screen caption in `#caption`). All app speech goes through it (`main.js speak`, `GameBase._speak`, `coach.js`); in-game `say()` and stories skip the caption because `#cue`/`#prompt` already show the text. Per-patient settings live in `store.getSettings/saveSettings` (captions, dwell time, capture-radius scale, squeeze ease → `tracker.setSqueezeEase`, high contrast, calm motion, text scale, practice mode, visual-field flag, per-bus volumes) and are edited in the staff drawer's Comfort section. Engine-level behaviors: `samplePos` respects the visual-field policy (comfort = bias spawns to the intact side; scan = train the cut side — hemianopia is independent of the reach envelope), `glow()` adds dark rims in high-contrast mode, `burst()` softens under calm motion, `miss()` is a no-op in practice mode (and `main.js#onRoundEnd` skips logging/DDA), the welcome skeleton goes dashed when not framed (amber/sage is a red-green confusion pair — never signal by that hue pair alone), and every 4th round (or a compensation spike) triggers a spoken rest suggestion. `audio.js` has `musicBus`/`fxBus` gains (`setVolumes`).

### Persistence

`storage.js`: single localStorage key `rehabsuite-v1`, per-patient records (per-arm profiles + assessment history, session rounds capped at 400, stars/unlocks, fatigue answers, `shoulderCm` = therapist tape-measured shoulder width entered once in the staff drawer — everything internal stays in SW units; `SW × shoulderCm` converts to real cm for the profile screen and export). Round records are appended by `main.js#onRoundEnd`; the therapist profile screen and JSON export read from here. Bump/migrate carefully — clinician data lives only in the browser.
